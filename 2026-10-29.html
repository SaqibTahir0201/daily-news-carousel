🤖 AI & AI AGENTS

Today's AI news has one honest theme: the industry stopped selling models and started selling the plumbing around models. Fusion is routing. The Copilot harness is an agent runtime. Long-running resilience is retry logic. None of that is machine learning. All of it is backend engineering. That is extremely good news for you.

The one that matters most: the managed agent harness

WHAT IS IT? Microsoft took the agent runtime it built for GitHub Copilot and made it rentable. In public preview, you declare an agent in Foundry Agent Service and Microsoft runs the agent loop and the sandbox. You supply four things:

  • Reusable skills — instructions, scripts and resources packaged as a procedure the agent can apply to many tasks.
  • Connected tools — Foundry tools and MCP tools, with authentication and approvals configured explicitly.
  • Execution and delegation — the agent can work with files and code, and hand bounded sub-tasks to built-in subagents while the main agent coordinates.
  • Source-controlled agent definitions — the agent lives in your repo next to your application code.

WHAT PROBLEM DOES IT SOLVE? Every team writes the same boring machinery: call the model, parse the tool call, run the tool, stuff the result back into context, decide whether to continue, stop before it loops forever, keep the context from exploding. It is undifferentiated work and most teams get the failure cases wrong.

HOW DOES IT WORK (simplified)? Conceptually it is a while-loop with guardrails:

while (!done && steps < MAX_STEPS && spend < BUDGET) {
  const reply = await model.call({ messages, tools });
  if (reply.toolCall) {
    if (needsApproval(reply.toolCall)) await askHuman(reply.toolCall);
    const result = await runTool(reply.toolCall);   // in a sandbox
    messages.push(result);                           // untrusted input!
  } else {
    done = true;
  }
  steps++;
}

That loop is the whole idea. The hard parts are the parts that look boring: step limits, spend limits, approvals, sandboxing, and context pruning when `messages` grows too large.

WHY ARE PEOPLE USING IT? Because agent reliability is mostly an infrastructure problem, and because the harness is model-agnostic (Microsoft says 20+ frontier models plus bring-your-own-key), so you can swap models without rewriting your orchestration.

WHY DOES IT MATTER TO ME? Because if you can write that loop properly in Node — with the limits, the approvals and the audit log — you are doing the job that is actually being hired for right now. "Prompt engineer" is not a job. "Engineer who can make an agent behave safely inside a production backend" very much is.

HOW COULD I USE IT IN A REAL PROJECT? Build the loop yourself in Express. One route POST /agent/run, three tools (search MongoDB, fetch a URL, send an email), a hard step limit of 10, a token-spend cap, and a rule that the email tool requires human approval. That single project touches tool calling, capability scoping, idempotency and observability.

WHAT SHOULD I LEARN? Tool calling, capability scoping, step/budget limits, and treating tool output as untrusted input.

DO I NEED TO LEARN THIS NOW? Yes — the concept and your own small implementation. No — not Azure Foundry's specific API.

RELEVANCE: 🟢 DIRECT  |  LEARNING PRIORITY: 🔥 HIGH  |  DEPTH: LEARN DEEPLY (the pattern), WATCH ONLY (the Azure product)

A term you will meet everywhere this year

TERM: Capability scoping (also called least-privilege tooling)
SIMPLE MEANING: Give an AI agent only the specific tools and permissions it needs for its job — nothing more.
REAL-WORLD EXAMPLE: A support agent that answers questions about orders gets a getOrder(orderId) tool. It does not get a runMongoQuery(query) tool, and it absolutely does not get deleteCustomer(). Notice that the first tool cannot be abused even if the model is fully tricked — the damage ceiling is built into the tool's shape.
WHY IT MATTERS: Prompt injection cannot be fully prevented, so you design so that a successful injection cannot do real harm. The tool surface is your real security boundary, not the system prompt.
WHY IT MATTERS TO ME: This is identical to how you already think about Express route authorisation. You know this instinct — you just have to apply it to tools instead of endpoints.

The interesting part is which docs they had to correct — several notes clarify how use cache, connection() and Suspense interact with Cache Components. That tells you where people are getting confused. So let's fix that for you properly.

WHAT IS CACHE COMPONENTS?

SIMPLE MEANING: A Next.js model where caching is something you opt into per piece of your page with an explicit use cache marker, instead of Next.js silently guessing what is static and what is dynamic.

WHY WAS IT CREATED? In the older model, a single accidental cookies() or headers() call made an entire route render dynamically — and you often didn't notice until production was slow. The caching rules were implicit and surprising. Developers could not answer the basic question "is this page cached or not?" by reading the code.

HOW DOES IT WORK (simply)? You mark the parts that can be cached. Everything else is dynamic by default. Each cached unit gets its own lifetime and its own revalidation. The uncached parts stream in afterwards, wrapped in Suspense — which is exactly why the docs needed that "note Suspense requirement for connection()" fix.

SIMPLE EXAMPLE — a product page where the product details are shared by everyone but the cart badge is per-user:

// cached: same for every visitor
async function ProductDetails({ id }) {
  'use cache';
  const product = await db.products.findOne({ _id: id });
  return <h1>{product.name}</h1>;
}

// dynamic: depends on this user's cookies
async function CartBadge() {
  const userId = (await cookies()).get('uid')?.value;
  const count = await db.carts.countDocuments({ userId });
  return <span>{count}</span>;
}

export default function Page({ params }) {
  return (
    <>
      <ProductDetails id={params.id} />
      <Suspense fallback={<span>…</span>}><CartBadge /></Suspense>
    </>
  );
}

The shell with the product name can be served instantly from cache to everyone; only the small user-specific piece waits on the database.

WHAT EXISTING CONCEPT DOES IT REPLACE? It replaces guessing. Previously: implicit static/dynamic inference plus scattered revalidate exports and route segment config. Now: an explicit boundary you can see in the code.

WHY SHOULD A NEXT.JS DEVELOPER CARE? Because "why is my page slow / why is my page stale" is the most common Next.js production problem, and this model makes the answer readable.

SHOULD I LEARN IT? HOW DEEPLY? Yes — LEARN DEEPLY, at the level of being able to draw your page as "cached shell + dynamic holes". RELEVANCE: 🟢 DIRECT  |  LEARNING PRIORITY: 🔥 HIGH

WHAT SHOULD I LEARN (specifically): use cache, cache lifetimes and tag-based revalidation, Suspense boundaries, and what forces a dynamic render (cookies(), headers(), connection()).

One more thing in your stack: OpenTelemetry traces in Next.js

TERM: Distributed tracing / span
SIMPLE MEANING: A trace is the full story of one request. A span is one chapter of it — "middleware ran", "page rendered", "Mongo query took 240 ms". Spans nest to show what caused what.
REAL-WORLD EXAMPLE: A page takes 3 seconds. The trace shows the render took 80 ms and one database query took 2.8 s. You now know exactly what to fix, instead of guessing from console.log.
WHY IT MATTERS: Once requests span several services, logs alone cannot tell you where the time went.
WHY IT MATTERS TO ME: This is the cheapest senior-looking skill you can acquire. Most mid-level developers debug performance with console logs; tracing is how it's done professionally — and once you add AI calls to your backend, a trace is the only sane way to see where the latency and cost actually went.
WHAT I SHOULD DO: Understand the basics now, then wire tracing into one project this month.

🏗️ TODAY'S SYSTEM DESIGN CONCEPT

Chosen because of a specific line in Microsoft's Foundry announcement: when a long-running agent gets interrupted and restarted with its original input, "your workflow also needs to prevent duplicate actions when work restarts". That one sentence is the whole concept.

CONCEPT: Idempotency

IN ONE SENTENCE: An operation is idempotent if running it five times leaves the system in exactly the same state as running it once.

WHAT PROBLEM DOES IT SOLVE? In any distributed system, requests get retried — the network times out, a worker crashes mid-job, a user double-clicks, a queue redelivers a message, an agent restarts from its original input. Without idempotency, every retry does the work again. That means duplicate orders, double charges, triple emails.

SIMPLE REAL-WORLD EXAMPLE: You click "Pay" and your connection drops before the response arrives. Did it work? You click again. A non-idempotent payment API charges you twice. An idempotent one recognises "this is the same payment attempt as before" and returns the original result.

HOW IT WORKS: The caller generates a unique idempotency key for the intent (not for the attempt) and sends it with every retry. The server stores the key with the result. On a repeat key, it skips the work and returns the stored result. Three rules that actually matter:

  1. The key must be created by the client, before the first attempt, and reused on every retry.
  2. The "store the key" and "do the work" steps must not be able to half-succeed — make the key insert the thing that guards the work.
  3. Keys expire. Store a result with them, not just a flag, or your retry gets an empty 200.

WHERE IS IT USED? Stripe's API (the canonical example), every message queue with at-least-once delivery, webhook receivers, and now agent frameworks that restart interrupted jobs.

HOW WOULD I USE IT WITH NODE / EXPRESS / MONGODB? The trick is to let MongoDB's unique index do the hard part:

// unique index once, at startup:
// db.idempotency.createIndex({ key: 1 }, { unique: true })

app.post('/orders', async (req, res) => {
  const key = req.header('Idempotency-Key');
  if (!key) return res.status(400).json({ error: 'Idempotency-Key required' });

  try {
    // Claim the key FIRST. The unique index makes this the lock.
    await db.collection('idempotency').insertOne({
      key, status: 'in_progress', createdAt: new Date()
    });
  } catch (e) {
    if (e.code !== 11000) throw e;                 // 11000 = duplicate key
    const prev = await db.collection('idempotency').findOne({ key });
    if (prev.status === 'in_progress') {
      return res.status(409).json({ error: 'request already in progress' });
    }
    return res.status(200).json(prev.response);    // replay the stored result
  }

  const order = await createOrder(req.body);       // the real work, once
  await db.collection('idempotency').updateOne(
    { key },
    { $set: { status: 'done', response: order } }
  );
  res.status(201).json(order);
});

COMMON MISTAKE: Generating the idempotency key on the server, or generating a new one per retry. Both are useless — the key must identify the intent, so the same user action always produces the same key. The second most common mistake: doing the work first and recording the key afterwards. Crash in between and you have done the work with no record of it, so the retry does it again.

WHAT I SHOULD BUILD TO LEARN IT: An Express endpoint that creates an order, plus a test script that fires the same request 50 times concurrently with the same key. Exactly one order must exist in MongoDB afterwards. If you get two, you have found a real race condition — that is the lesson.

DIFFICULTY: Intermediate

WHY IT MATTERS TO ME: You cannot build a reliable payment flow, webhook handler, job queue or AI agent without this. It is also one of the most common backend interview questions that filters mid-level from senior.

🎨 CREATIVE DEVELOPMENT

The big one: React Three Fiber v10 makes WebGPU the default

WHAT HAPPENED: In the v10 alpha line, R3F stopped treating WebGPU as opt-in. In alpha 5 you enabled it with a <Canvas renderer> prop. In alpha 6 the maintainers decided a major version is the right moment to break it: the default <Canvas> now uses the new renderer, and the old WebGL-only path moved to @react-three/fiber/legacy. Their reasoning, quoted: node materials, compute shaders and the rendering pipeline only function in the new renderer, and Three.js itself is mostly focused on WebGPU and TSL now. Status: EARLY / EMERGING (alpha).

The migration is genuinely small:

// Have custom GLSL or WebGL-only libraries? One import change:
- import { Canvas } from '@react-three/fiber'
+ import { Canvas } from '@react-three/fiber/legacy'

Other changes worth knowing: TSL hooks (useUniforms, useNodes, useGPUStorage, useRenderPipeline…) moved to a new @react-three/tsl package; <Canvas shadows> became renderer={{ shadows }}; physics-phase jobs now run on a fixed timestep; onUpdate was removed; @react-three/fiber/webgpu is deprecated.

WHAT IS WEBGPU?

SIMPLE MEANING: The replacement for WebGL. It is a newer browser API for talking to the graphics card that matches how modern GPUs actually work, is cheaper to drive from JavaScript, and — crucially — adds compute shaders, which WebGL never had.

WHY IS IT BECOMING IMPORTANT NOW? Coverage. It has been default-on in Chrome and Edge since v113 across Windows, macOS, ChromeOS and Android, and Safari 26 added it on Apple platforms. Roughly 95% of users now have a WebGPU-capable browser, and Three.js falls back to WebGL 2 automatically for the rest. The "I can't ship it" excuse expired.

WHAT IS A COMPUTE SHADER?

SIMPLE MEANING: A program that runs on the GPU without drawing anything. It just does maths on large arrays, massively in parallel, and writes the results into GPU memory.

REAL-WORLD EXAMPLE: 100,000 particles. In WebGL you had to fake it by encoding positions into floating-point textures and ping-ponging framebuffers — workable and genuinely unpleasant. With a compute shader, the particle positions live in a GPU buffer and never travel to JavaScript at all:

import { Fn, storage, instanceIndex, float } from 'three/tsl'

const count = 100000
const positions = new THREE.StorageInstancedBufferAttribute(count, 3)
const positionStorage = storage(positions, 'vec3', count)

const updateParticles = Fn(() => {
  const pos = positionStorage.element(instanceIndex)
  pos.y.addAssign(float(0.01))      // every particle, in parallel, on the GPU
})().compute(count)

renderer.computeAsync(updateParticles)   // once per frame

WHY IT MATTERS FOR CREATIVE DEVELOPMENT: This is the dividing line between "nice Three.js scene" and the Awwwards-tier work you are aiming at. Large particle fields, fluid-like motion, GPU physics, crowd simulation — all of it needs compute. Be clear-eyed about one thing: compute shaders are WebGPU-only and do not fall back. If your visual depends on compute, you must design a deliberately simpler experience for WebGL visitors — designed up front, not discovered in production.

WHAT IS TSL (Three.js Shading Language)?

SIMPLE MEANING: TSL lets you write shaders in JavaScript. You import small building blocks (nodes) from three/tsl, combine them with ordinary JavaScript, and Three.js compiles the result into WGSL for WebGPU or GLSL for the WebGL 2 fallback. One source, both backends, chosen at runtime by whatever the visitor's browser supports.

WHY WAS IT CREATED? Two real problems. First, WebGL speaks GLSL and WebGPU speaks WGSL, and they are not close enough for find-and-replace — supporting both by hand means writing and debugging every custom material twice, forever. Second, if you wanted Three.js's standard lighting plus one custom effect, the old technique was onBeforeCompile: string-replacing fragments of Three.js's own shader source. It broke on every Three.js upgrade, couldn't compose with anything else, and nobody ever remembered how it worked.

THE ONE IDEA TO INTERNALISE: in TSL you are not writing code that runs — you are building an expression that gets compiled. uv().x.mul(2.0) multiplies nothing when that line executes; it constructs a node meaning "the x component of the UV, times two". Three.js walks that graph later and emits WGSL or GLSL.

Everything else follows from that:

  • Operators are methods, because JavaScript cannot overload *: a.mul(b).add(c) instead of a * b + c.
  • Swizzling is properties: .x, .xy, .rgb work as in GLSL.
  • Built-in nodes replace uniform plumbing: time, uv(), positionLocal, normalWorld, cameraPosition, screenUV, instanceIndex — no per-frame update code.
  • Control flow is explicit: JavaScript's if/for/Math.sin run once, on the CPU, while building the graph. Use TSL's If, Loop and sin when the decision must happen on the GPU, per pixel.

A complete animated gradient, in JavaScript:

import { uv, vec3, mix, sin, time } from 'three/tsl'

const t = sin(time).mul(0.5).add(0.5)                      // 0..1 oscillation
const gradient = mix(vec3(0.1,0.2,0.4), vec3(0.9,0.4,0.2), uv().x)
material.colorNode = gradient.mul(t)

ONE IMPORTANT WARNING: ShaderMaterial, RawShaderMaterial and onBeforeCompile do not work with WebGPURenderer. They are GLSL, and this renderer has no GLSL to patch. Your GLSL knowledge is not wasted — every concept (UVs, noise, smoothstep, fresnel) transfers directly — but the code itself must be rewritten in TSL.

Most of the translation is mechanical: a * b + c → a.mul(b).add(c), vUv → uv(), uniform float uTime → time, 1.0 - x → oneMinus(x), gl_FragColor = … → material.colorNode = …, vertex displacement → material.positionNode = …, if/else → If(c, () => {}).Else(() => {}).

WHAT CAN I BUILD WITH IT? A 100k-particle GPU field that reacts to the mouse. A liquid-metal hero section. Node-based post-processing (bloom that only picks up what glows). Instanced skinned characters — Three.js r185 added a TSL helper that computes skeletal animation inside custom compute passes, which means crowds and swarms that were CPU-bound are now GPU territory.

WHAT SHOULD I LEARN FIRST? In this order: (1) the node/graph mental model, (2) rewrite one GLSL shader you already understand into TSL, (3) then compute shaders. Do not start with compute.

WHY SHOULD I CARE? You already have React and you want Awwwards-level work. R3F v10 + TSL is exactly the intersection of those two. And because it is alpha right now, learning it now means you are early rather than catching up.

RELEVANCE: 🟢 DIRECT  |  LEARNING PRIORITY: 🔥 HIGH  |  DEPTH: LEARN DEEPLY (TSL), EXPERIMENT (R3F v10 alpha — do not ship it)

🛡️ CYBERSECURITY

1. The npm worm that targets AI coding tools

WHAT HAPPENED: SafeDep spotted the "testmetest" npm campaign (18 packages published by one operator between 19 and 25 October) and initially concluded it was a test with no victims. JFrog's follow-up analysis proved otherwise: the operator had already armed 42 real GitHub repositories belonging to 11 owners, with account hijacking starting as early as July. It shares code with June's Miasma Phantom Gyp worm and adds Mini Shai-Hulud's token-revocation wiper. Status: CONFIRMED (JFrog research).

WHAT IS THE VULNERABILITY?

TERM: Supply-chain attack via install scripts
SIMPLE MEANING: npm packages can declare scripts that run automatically during npm install — before any of your code imports them, and before your tests or security checks run. A malicious package uses that moment to steal every credential on the machine.
REAL-WORLD EXAMPLE: Microsoft documented the ChainDrop campaign doing exactly this across more than 400 packages, including widely used ones like keyv, flat-cache and cache-manager. The payload ran from a preinstall hook, hunted for npm, GitHub, AWS, Kubernetes and HashiCorp Vault credentials, then used stolen npm tokens to republish other packages with itself inside — a worm. In the Tensorlake incident on 8 October, the malicious version was flagged by Socket about eleven minutes after publication, which is fast, and still plenty of time.
WHY IT MATTERS: Your laptop and your CI runner usually hold more credentials than your production server does.

HOW DOES THE ATTACK WORK (defensive view only): three stages worth understanding, because each one suggests a defence.

  1. Execution before inspection. The payload runs from a preinstall hook, so it executes on install, not on import. Defence: disable install scripts.
  2. Credential sweep plus a new twist. It collects cloud, CI and registry credentials — and now also harvests and poisons the configuration files of AI coding tools (Claude, Gemini, Cursor, VS Code, Zed), planting execution hooks there for persistence and creating a developer-to-developer infection path. Defence: treat those config files as security-sensitive; review them in code review.
  3. The "hostage token". The malware watches the stolen GitHub token. If you revoke it, destructive commands fire — in these families, wiping the home directory. Defence: remove persistence before revoking any credential, and revoke from a different machine.

WHO IS AFFECTED? Anyone who runs npm install. Note the MALFEX campaign separately: as of 1 October, function-flag, function-color and cdn-img-fetch were still live and installable on npm, two of them with no advisory at all — 40,767 total downloads across the operator's malicious packages. Absence of an advisory is not evidence of safety.

WHY SHOULD A MERN DEVELOPER CARE? Because your dependency tree is thousands of packages deep, you install daily, and AI coding agents now add dependencies automatically with less human review than ever. That last point is the new multiplier.

HOW DO I PROTECT MY APPLICATION?

  1. npm config set ignore-scripts true globally. Re-enable per project only when a package genuinely needs to compile native code. This single setting defeats the whole preinstall class.
  2. Always commit and install from a lockfile; use npm ci in CI, never npm install.
  3. Pin exact versions for anything in your critical path. Most of these attacks arrive as an innocuous-looking patch bump.
  4. Never put a long-lived npm or GitHub token on your laptop. Use short-lived tokens and OIDC-based publishing in CI.
  5. Give CI jobs the narrowest possible permissions — the worm's power came from what the stolen identity could reach, not from the code itself.
  6. Put your AI tool config files under review. They are executable surface now.

SAFE PRACTICAL LAB: In a throwaway folder, create a package with a preinstall script that only prints process.env keys (names only, never values) to a local file. Install it. See how much it learned before you wrote a single line of app code. Then set ignore-scripts true, install again, and watch the file stay empty. That five-minute experiment will permanently change how you feel about npm install.

RELEVANCE: 🟢 DIRECT  |  LEARNING PRIORITY: 🔥 HIGH

2. SlugFest: npm Trusted Publishing could be hijacked via abandoned repo names

WHAT HAPPENED: Bloom Security found a flaw, dubbed SlugFest, in npm's Trusted Publishing. npm verified trusted publishers using the human-readable GitHub owner/repo name instead of the repository's permanent numeric ID. When a repo is renamed, transferred or deleted, that name can be claimed by someone else — who could then create a repository at that address, add a workflow with the expected filename, and obtain valid publishing credentials for a package they never owned. Over 1,500 packages were potentially affected, including security scanners, authentication tools and cryptographic packages, with more than 10 million combined downloads. Status: CONFIRMED and FIXED — GitHub shipped a fix on 2 October introducing a 48-hour expiry for unvalidated Trusted Publishing configurations, and npm now rejects trusted-publishing tokens issued through issue_comment events. Bloom reported no exploitation in the wild, but did successfully publish a new version of a real package under controlled testing.

WHAT IS TRUSTED PUBLISHING?

TERM: Trusted Publishing / OIDC
SIMPLE MEANING: Instead of storing a long-lived npm publish token in your CI secrets, your CI pipeline proves its identity to npm cryptographically at publish time and receives a short-lived credential. OIDC (OpenID Connect) is the protocol that does the proving.
REAL-WORLD EXAMPLE: Rather than "here is my password", it's "GitHub Actions vouches, right now, that this job is running in repo X on workflow Y". No secret to steal.
WHY IT MATTERS: It removes the single most valuable thing a worm can steal. It is the correct answer to story #1.
WHY IT MATTERS TO ME: If you ever publish an npm package, use this instead of a token. And the bug here teaches a deeper lesson you can apply directly to your own code: never key authorisation on a mutable, human-readable name when a stable immutable ID exists. That exact bug shape appears in MERN apps all the time — authorising by username or email instead of by user _id, or by MongoDB collection slug instead of ObjectId. Rename or re-register, and someone inherits the old identity's permissions.
WHAT I SHOULD DO: Learn the pattern. Then grep your own projects for authorisation checks that compare names or emails instead of IDs.

RELEVANCE: 🟢 DIRECT (the design lesson)  |  LEARNING PRIORITY: 🟠 MEDIUM

3. The Anthropic incident, as a security lesson

WHY SHOULD A MERN DEVELOPER CARE? Cathedral's agents didn't break Anthropic's code. They walked in through third-party admin and sales tools — the kind of SaaS every company connects and forgets. Anthropic's own red teamer made the point that matters: attackers can now run agents continuously against a company's external dependencies at low cost. Your security perimeter includes every vendor you handed an OAuth token to.

HOW DO I PROTECT MY APPLICATION? Inventory your integrations. For each one ask: what scope did I grant, is it still needed, when was the token last rotated, and what happens if that vendor is compromised? Prefer read-only scopes. Prefer short-lived tokens. Remove integrations you stopped using — an unused integration with a live token is pure downside.
