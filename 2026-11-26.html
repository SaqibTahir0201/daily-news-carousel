1. 1Password got hacked through a stolen GitHub account — vaults are safe, but the attack path is exactly how your projects would get hacked

WHAT HAPPENED:

1Password (the password manager company) confirmed on 25 November that an attacker got into one employee's corporate GitHub account on 19 November. From that single account, the attacker read private source code, pushed malicious code into backend services, got into the CI/CD system, and downloaded customer names, sign-in email addresses and account metadata for a subset of users. Customer vaults, vault keys, account passwords and Secret Keys were not touched — 1Password does not store those. Status: CONFIRMED (official 1Password blog, 25 Nov; TechCrunch, The Verge).

WHAT IS THIS?

TERM:

Supply-chain attack (software supply chain)

SIMPLE MEANING:

Instead of attacking your running app directly, the attacker attacks something your app trusts — your code repo, your build pipeline, or a package you install — and lets your own system deliver the malicious code for them.

REAL-WORLD EXAMPLE:

Nobody broke into 1Password's servers from the outside. One developer's GitHub account was taken over, and then 1Password's own deploy pipeline obediently shipped the attacker's code to production.

WHY IT MATTERS:

A dev account plus an automated pipeline equals production write access. Most teams protect production servers carefully and protect developer accounts carelessly.

WHY IT MATTERS TO ME:

You use Git/GitHub and you deploy. You almost certainly have a GitHub token sitting somewhere with repo + workflow scope, and a deploy that runs automatically on push to main. That is the exact shape of this attack.

RELEVANCE: 🟢 DIRECT

IMPORTANCE: 🔥 HIGH

WHAT I SHOULD DO: Today, audit your own GitHub: enable 2FA with an authenticator or passkey, delete personal access tokens you don't use, and check which tokens have workflow scope. See the Cybersecurity section for the full checklist.

2. Google's AI agent published six math proofs in one day — the maths is irrelevant to you, the architecture is not

WHAT HAPPENED:

On 25 November, Google Research pushed six research papers (274 pages total) to a public GitHub folder, all produced by Cogentic — a multi-agent system built on Gemini 4. The headline claim is a proven integer-factorization bound that closes a 34-year-old theoretical gap. Status: ANNOUNCED / EARLY — these are preprints in a GitHub folder, not peer reviewed, and the promised Lean (computer-checked) proofs were not public at time of writing.

WHAT IS THIS?

TERM:

Multi-agent harness (prove–verify loop)

SIMPLE MEANING:

Instead of one AI answering once, you build a system: one agent proposes a solution, another agent checks it, and the loop repeats until the checker is satisfied. The "harness" is the orchestration code around the model — the thing that decides who runs when, what gets retried, and when to stop.

REAL-WORLD EXAMPLE:

Cogentic: a generator agent writes a proof step, a verifier agent tries to break it, failures feed back in, and the loop runs until the proof survives.

WHY IT MATTERS:

This is the single most important pattern in agentic AI right now — the quality came from the loop and the verifier, not from the model being smarter.

WHY IT MATTERS TO ME:

This is 100% a backend engineering problem, and backend is your lane. A prove–verify loop is a queue, a worker, a retry policy and a validation step. You can build the same shape in Node.js this week.

RELEVANCE: 🟡 RELATED (the maths: ⚪ NOT IMPORTANT. The architecture: 🟢 DIRECT)

IMPORTANCE: 🔥 HIGH (for the pattern only)

WHAT I SHOULD DO: Ignore the number theory completely. Steal the generator→verifier→retry loop and build a tiny version with Node + a queue.

SIMPLE MEANING:

WHY IT MATTERS:

WHY IT MATTERS TO ME:

You are a Node/MERN developer. npm install is something you run several times a day, often without reading what changed. You also build AI agent stuff with MCP — which is now explicitly in attackers' crosshairs.

RELEVANCE: 🟢 DIRECT

Confidential computing

SIMPLE MEANING:

Normally data is encrypted when it's stored and when it travels, but it must be decrypted in memory to actually be processed. Confidential computing keeps it encrypted even while being processed, inside a hardware-isolated region of the chip that even the cloud provider can't read into.

WHY IT MATTERS TO ME:

A number that measures how well a language model predicts the next piece of text. Lower is better. It's a rough proxy for raw model capability.

SIMPLE MEANING:

TSL lets you write GPU shader logic in JavaScript instead of writing GLSL or WGSL by hand. You compose small node objects — uv(), texture(), mix(), sin() — like building an expression tree, and Three.js compiles that tree down to GLSL (for WebGL) or WGSL (for WebGPU) automatically.

REAL-WORLD EXAMPLE:


import { texture, uv, time, sin, mix, vec3 } from 'three/tsl';

const wobble = sin( uv().x.mul( 20 ).add( time ) ).mul( 0.5 ).add( 0.5 );
material.colorNode = mix( vec3( 1, 0, 0 ), texture( map, uv() ), wobble );

That's an animated shader effect, in JavaScript, with no GLSL string anywhere.

🤖 AI & AI AGENTS

Agent evals — the thing that turns prompt-tweaking into engineering

WHAT IS IT?

An eval is a repeatable, scored test for an AI system. You define a task, define what "good" looks like, run the agent, and score it. Run the same eval after every change.

WHAT PROBLEM DOES IT SOLVE?

AI output is non-deterministic. The same prompt gives different answers each run. So "I tried it once and it worked" tells you nothing. Without evals you are flying blind: you change a prompt, something else breaks silently, and you find out from a user.

HOW DOES IT WORK?

Simplified: you build a dataset of test cases. For each, you store the task input and a rubric (the rules for what counts as a pass). You run the agent N times per case. You score each run — either with a programmatic check (did it call the right tool? is the JSON valid? does the number match?) or with an LLM-as-judge (a second model reads the output and grades it against the rubric). You aggregate into a pass rate. You compare pass rates between versions.

TERM:

LLM-as-judge

SIMPLE MEANING:

Using a second language model to grade the first one's output against written criteria, because the correct answer is a paragraph rather than an exact value you can === compare.

REAL-WORLD EXAMPLE:

Your agent summarises a support ticket. There's no single correct summary. So a judge model checks: "Does it name the customer's actual problem? Is it under 50 words? Does it avoid inventing facts?" and returns pass/fail per criterion.

WHY IT MATTERS:

It makes subjective quality measurable — imperfectly, but measurably.

WHY ARE PEOPLE USING IT?

Because it's the only way to ship AI features with confidence. Note what happened above: GitHub shipped Evals as a product, and Cogentic's whole result came from a verify loop. Both are the same insight — the checker is the product.

WHY DOES IT MATTER TO ME?

You already know how to write tests and run CI. Evals are tests with fuzzy assertions. You are better positioned to learn this than most AI hobbyists, because you have the backend and CI instincts already. This is your competitive edge in AI work.

HOW COULD I USE IT IN A REAL PROJECT?

Take any agent or AI endpoint you've built. Create evals/cases.json with 10 realistic inputs and a rubric for each. Write a Node script that runs each case 3 times, scores it with a cheap judge model, prints a pass-rate table, and exits non-zero if the rate drops below your threshold. Wire it into GitHub Actions. You now have CI for AI.

WHAT SHOULD I LEARN? Eval dataset design, programmatic vs. judge scoring, pass@k, and regression comparison.

DO I NEED TO LEARN THIS NOW? Yes. This is the highest-value AI skill available to a backend developer today.

RELEVANCE: 🟢 DIRECT — LEARNING PRIORITY: 🔥 HIGH — LEARN DEEPLY

npm ci vs npm install — the one-line change that reduces your supply-chain risk

WHAT IS IT?

npm install is allowed to resolve newer versions within your semver ranges and will rewrite your lockfile. npm ci installs exactly what package-lock.json says, fails if the lockfile and package.json disagree, and never updates anything.

WHY DOES IT MATTER?

Re-read finding #1 from the Databricks report: compromised legitimate packages were 7% of malicious packages but over 99% of downloads. That means the risk isn't mostly weird new packages — it's a poisoned new version of something you already trust. npm install can pull that silently. npm ci cannot.

SIMPLE EXAMPLE:


# local, when you intend to change dependencies
npm install

# CI, Docker builds, production deploys — always
npm ci

And when you do update: npm outdated, then update deliberately, then read the diff for anything suspicious before committing the lockfile.

🏗️ TODAY'S SYSTEM DESIGN CONCEPT

CONCEPT:

Generate–Verify Loop (with bounded retries)

IN ONE SENTENCE:

Instead of trusting a job's output the first time, you run a separate checking step, and if the check fails you feed the failure back and try again — up to a hard limit.

WHAT PROBLEM DOES IT SOLVE?

Some operations are unreliable by nature: an LLM call, an OCR pass, a scrape, an external API that sometimes returns garbage. You can't make the generator perfect. But you can make the system reliable by making the checker strict and the retry informed. This is exactly the architecture behind both of today's big AI stories — Cogentic's proof loop and GitHub's Evals.

SIMPLE REAL-WORLD EXAMPLE:

You build "upload an invoice PDF, get structured JSON". The model gets it right about 80% of the time. Instead of shipping 80%, you add a verifier: does the JSON match the schema? Do the line items sum to the stated total? Is the date a real date? If any check fails, you re-prompt the model with the specific failure ("the line items sum to 4,230 but total says 4,320 — recheck"). Your accuracy climbs sharply, and the 20% failures become visible instead of silent.

HOW IT WORKS:

1. A job lands on a queue with attempt: 0.

2. A worker picks it up and runs the generator (LLM call, parse, whatever).

3. The output goes to the verifier — a pure, cheap, deterministic function wherever possible.

4. Pass → write result, mark job done.

5. Fail → increment attempt. If attempt < maxAttempts, re-enqueue with the failure reason attached so the next run has more information than the last. Use exponential backoff for delay.

6. attempt >= maxAttempts → move to a dead letter queue and alert. Never retry forever.

TERM:

Dead letter queue (DLQ)

SIMPLE MEANING:

A separate holding queue for jobs that failed too many times. They stop being retried and sit there so a human can look at them.

WHY IT MATTERS:

Without a DLQ, a permanently-broken job retries forever, burns money and clogs your workers. With one, failures become a small reviewable list.

TERM:

Idempotency

SIMPLE MEANING:

Running the same operation twice produces the same end state as running it once.

REAL-WORLD EXAMPLE:

If a verification retry re-runs a job that already inserted a MongoDB record, you now have duplicates. Give each job a stable jobId and use updateOne({ jobId }, { $set: {...} }, { upsert: true }) so a retry overwrites instead of duplicating.

WHY IT MATTERS:

Retries are only safe if your writes are idempotent. Adding retries to a non-idempotent system creates data corruption, not reliability.

WHERE IS IT USED?

Cogentic's proof loop. Stripe's webhook delivery. Any serious document-extraction pipeline. CI test retries. Email delivery systems.

HOW WOULD I USE IT WITH NODE/EXPRESS/MONGODB?


// Minimal shape — concepts, not production code
const MAX_ATTEMPTS = 3;

async function processJob(job) {
  const result = await generate(job.input, job.lastFailure);  // feed failure back
  const check = verify(result);                                // cheap + deterministic

  if (check.ok) {
    await db.collection('results').updateOne(
      { jobId: job.jobId },                 // idempotency key
      { $set: { result, status: 'done' } },
      { upsert: true }
    );
    return;
  }

  if (job.attempt + 1 >= MAX_ATTEMPTS) {
    await db.collection('dlq').insertOne({ ...job, lastFailure: check.reason });
    return;
  }

  await queue.add(
    { ...job, attempt: job.attempt + 1, lastFailure: check.reason },
    { delay: 1000 * Math.pow(2, job.attempt) }   // exponential backoff
  );
}

Use BullMQ (Redis-backed) as the queue — it gives you attempts, backoff and a failed-jobs view out of the box, so you can focus on writing the verifier.

COMMON MISTAKE:

Making the verifier an LLM call when a plain function would do. If you can check it with a schema, a sum, a regex or a type, do that — it's free, instant, and it can't hallucinate a pass. Reach for an LLM judge only for genuinely subjective criteria. The second most common mistake: retrying without passing the failure reason back, so attempt 3 is just as blind as attempt 1.

WHAT I SHOULD BUILD TO LEARN IT:

An Express endpoint that accepts text and returns structured JSON, with a Zod schema as the verifier, BullMQ for the queue, 3 max attempts with exponential backoff, a /dlq route to list permanent failures, and a MongoDB upsert keyed on jobId. This one small project teaches you queues, workers, retries, backoff, idempotency, DLQs and AI reliability at the same time.

🎨 CREATIVE DEVELOPMENT

TSL is now the centre of gravity in Three.js — and the compiler is getting serious

WHAT IS IT?

TSL (Three.js Shading Language) is a system inside Three.js that lets you build GPU/shader logic using a node-based, JavaScript-style API instead of writing shader code as strings. You compose small typed nodes — uv(), time, texture(), mix(), vec3(), with chainable maths like .mul(), .add(), .sin() — into an expression graph, and Three.js compiles that graph into GLSL for WebGLRenderer or WGSL for WebGPURenderer.

TERM:

Shader

SIMPLE MEANING:

A small program that runs on the GPU, once per vertex or once per pixel, massively in parallel. Vertex shaders decide where things are; fragment shaders decide what colour each pixel is.

TERM:

GLSL vs WGSL

SIMPLE MEANING:

GLSL is the shader language WebGL uses. WGSL is the shader language WebGPU uses. They are different languages for the same job, which is why a hand-written GLSL effect does not work on WebGPU.

TERM:

Dead code elimination

SIMPLE MEANING:

A compiler optimisation that removes code whose result is never used, so it never gets compiled or executed.

REAL-WORLD EXAMPLE:

Your TSL graph builds three colour variations but the final colorNode only uses one. Previously those unused branches could still end up in the generated shader, costing GPU work every frame. Now they're stripped.

WHY IT MATTERS:

A GPU shader runs for every pixel, every frame — perhaps 2 million times per frame at 60fps. Unused work there is expensive in a way unused work in Node.js is not.

WHY IT MATTERS TO ME:

It signals that TSL is no longer an experiment. Adding dead code elimination, deferred texture methods and a separated method-chaining prototype is what you do when you expect people to ship production sites on it. This is a safe thing to invest learning time in.

WHY IS IT BECOMING IMPORTANT?

Because WebGPU is the future of browser graphics and WebGPU needs WGSL. TSL is the only practical way to write one effect that runs on both renderers. It is also how you access GPU compute (running general parallel calculations on the GPU — particles, physics, simulations) from Three.js, which WebGL essentially can't do properly.

WHAT CAN IT DO?

Custom materials, post-processing effects, procedural textures, vertex displacement, instanced-mesh effects, and compute-driven particle systems — in JavaScript, with autocomplete and type coercion, cross-renderer.

WHAT CAN I BUILD WITH IT?

Start small and real: a scroll-driven displacement effect on an image plane; a procedural animated gradient background; a glass/refraction material; then a GPU particle system driven by a compute shader. That last one is exactly the kind of thing that wins Awwwards.

WHAT SHOULD I LEARN FIRST?

In this order: (1) uv() and how UV coordinates work; (2) time and simple animation with sin(); (3) mix() for blending; (4) texture() and sampling; (5) colorNode vs positionNode; (6) only then compute. Import from three/tsl and three/webgpu.

Upgrade warning before you touch r188

If you upgrade past r187, expect visual changes to existing scenes, not just API breaks. From the official migration guide for 187 → 188: AmbientLight and HemisphereLight now add specular reflections to MeshStandardMaterial/MeshPhysicalMaterial (metals no longer render black without an env map, rough surfaces brighten at grazing angles — if you use these as fill lights alongside an env map, lower their intensity); multi-bounce ambient occlusion noticeably weakens occlusion on bright and metallic surfaces for all AO sources (compensate by raising GTAONode.scale/SSAONode.intensity, or re-bake/darken your aoMap — do not push aoMapIntensity above 1, its range is [0,1] and higher values produce artifacts); iblIrradiance removed; LightProbe deprecated in favour of Scene.environment or a LightProbeGrid. Also note from 186 → 187: CubeUVReflectionMapping removed, PMREMs rebuilt on cube render targets so env-lit materials look slightly different, and TSL struct storage buffers are always arrays now (storage.element(0).get('member')).

The practical rule the Three.js team states: upgrade in increments of 10 releases, because deprecation warnings only last 10 releases.

RELEVANCE: 🟢 DIRECT — LEARNING PRIORITY: 🔥 HIGH — LEARN DEEPLY (TSL), WATCH ONLY (the r188 lighting details, until you actually upgrade)

🛡️ CYBERSECURITY

The 1Password incident — read this as a blueprint of how you'd get hacked

WHAT HAPPENED?

19 November: an attacker had access to a 1Password employee's corporate GitHub account. They used it to read private source code, push malicious code to backend services, and reach the CI/CD system. The malicious code downloaded customer account records: names, sign-in email addresses, account/user identifiers, account creation and last sign-in times, public keys, SRP protocol parameters, tokens embedded in invitation/provisioning/recovery email links, and internal metadata. Disclosed 25 November.

WHAT IS THE VULNERABILITY?

There wasn't a code bug. The vulnerability was trust topology: a developer identity had a path, via automation, to production code execution. One account compromise became production write access.

HOW DOES THE ATTACK WORK (defensive view)?

Get a developer's source-control account → push code into a branch that the pipeline deploys → the organisation's own trusted automation runs your code with production credentials → collect data from inside. The attacker never fought the perimeter, because the perimeter was configured to let the pipeline through.

WHO IS AFFECTED?

A subset of 1Password customers (count not disclosed). Vaults, vault keys, account passwords, Secret Keys and recovery keys were not affected — 1Password doesn't store them, so there was nothing to take. The apps and browser extensions are unaffected.

WHY SHOULD A MERN DEVELOPER CARE?

Because your setup has the same shape. You push to GitHub, something deploys automatically, and secrets live in CI. Also note what saved 1Password's customers: end-to-end encryption meant the company itself couldn't read the valuable data, so neither could the attacker. That's an architecture decision, made years earlier, that limited the blast radius of a total backend compromise. That is the real lesson.

TERM:

Blast radius

SIMPLE MEANING:

How much damage one compromised thing can cause. Small blast radius means breaking one piece doesn't break everything.

REAL-WORLD EXAMPLE:

1Password's backend was fully compromised and customer passwords were still safe, because the backend never had the keys. Compare that to a typical app where the database contains everything in readable form.

WHY IT MATTERS TO ME:

When you design, ask "if this component is fully owned, what does the attacker get?" If the answer is "everything", redesign.

HOW DO I PROTECT MY APPLICATION — do these today:

1. GitHub 2FA on a passkey or authenticator app, not SMS. Check every org you belong to.

2. Audit personal access tokens. Delete unused ones. Any token with workflow scope can modify your CI, which means it can run arbitrary code with your secrets. If you have a long-lived broad token sitting in a file, replace it with a fine-grained token, minimum scopes, short expiry.

3. Branch protection on main — require PR review, and don't let the deploy pipeline trigger on arbitrary branches.

4. Scope CI secrets per environment. Production secrets should not be readable by a workflow triggered from a feature branch or a fork.

5. Rotate secrets on a schedule, so a quiet leak has a shelf life.

6. Store the least you can. Hash passwords (argon2/bcrypt). Don't store card numbers. Encrypt client-side where feasible.

7. Expect phishing. 1Password specifically warns about unexpected emails/texts/calls about invitations or account recovery, and notes they will never ask for your account password or Secret Key. Since attackers now hold real names paired with real sign-in addresses, the next wave of phishing will look convincing.

WHAT SHOULD I LEARN? Least-privilege CI/CD design, GitHub fine-grained tokens and branch protection, and the general habit of blast-radius thinking.

SAFE PRACTICAL LAB (do this locally, 30 min):

Create a throwaway repo. Add a GitHub Actions workflow that prints ${{ secrets.TEST_SECRET }} masked and lists its environment. Now try to read that secret from a workflow triggered by a pull request from a fork — observe that it's blocked, and understand why GitHub blocks it. Then set up an environment with a required reviewer and watch the deploy job wait for approval. You'll learn more about pipeline security in half an hour than from any article.

RELEVANCE: 🟢 DIRECT — LEARNING PRIORITY: 🔥 HIGH

npm supply chain — the numbers you should remember

From the Databricks analysis (23 Nov) of ~5,400 malicious npm packages, Dec 2025 – Oct 2026:

  • 89% of malicious packages are attacker-created, but they account for only 0.2% of malicious downloads. 7% are compromised legitimate packages and they account for over 99% of downloads. → The danger is a bad version of a package you already trust, not a weird new name.
  • Only 54% declare a lifecycle (install) script; the rest execute on import or invocation. → Disabling install scripts is useful but not sufficient. Code can fire on require().
  • Account compromise has shifted from stolen tokens to compromised build pipelines. Of malicious packages published via OIDC trusted publishing, 85% were compromised legitimate packages. → Same lesson as 1Password: the pipeline is the target.
  • 38% of malicious packages talk to legitimate third-party services (serverless hosts, chat webhooks, paste sites, public blockchain RPC nodes as dead-drop resolvers). → Domain reputation won't catch it; the traffic looks like normal developer traffic.
  • Median time from publication to public advisory for unattributed packages: 1.7 days. Median registry takedown: 7 days, with 10% exceeding 59 days. 16% were still installable at analysis time. → You cannot rely on the registry to protect you in time.

TERM:

Dead drop resolver

SIMPLE MEANING:

Instead of hardcoding the attacker's server address (which gets blocked), the malware reads an address from somewhere public and innocent-looking — a blockchain transaction, a paste site, a social media bio — and goes wherever that says.

REAL-WORLD EXAMPLE:

The @adminide-stack malware read the latest transaction from an Ethereum wallet and converted the destination address into an IPv4 address for its command server.

WHY IT MATTERS:

The attacker can move their server at will and the malware follows, with no update needed. Blocking one IP achieves nothing.

WHY IT MATTERS TO ME:

It explains why "we blocked the bad domain" is not remediation. Containment has to be about credentials and rotation, not addresses.

HOW DO I PROTECT MY APPLICATION:

1. npm ci everywhere that isn't you deliberately changing dependencies.

2. Commit package-lock.json. Always.

3. npm audit / Dependabot alerts on, but don't trust them as your only layer — the median advisory lag is days.

4. Consider --ignore-scripts in CI where your build doesn't need them.

5. Before adding a dependency: check weekly downloads, last publish date, number of maintainers, and whether the repo looks real. Be extra careful with anything matching a popular package name with a small twist (clampony vs clamp).

6. Don't run npm install as root, and don't run untrusted installs on a machine holding your production credentials.
