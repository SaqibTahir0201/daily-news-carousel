WHAT HAPPENED: Seven CVEs, patched 3 November. Netlify published the full table. WHY IT MATTERS TO ME: This is your framework. And when you build multi-tenant SaaS in MERN, you will write your own Redis cache keys — the same bug class applies to your Express code.

💻 MERN / JAVASCRIPT / WEB

Next.js Cache Components — what it actually is

Today's CVEs are all about this feature, so let's finally understand it properly.

WHAT IS CACHE COMPONENTS? A Next.js system where you mark a function or component with 'use cache' and Next.js saves its rendered output. Next time someone needs it, it's served from memory instead of being recomputed.

WHY WAS IT CREATED? Before this, Next.js caching was confusing — it happened implicitly in fetch(), in route segments, in unstable_cache, each with different rules. Developers couldn't predict what was cached. Cache Components makes it explicit: you write 'use cache', you know it's cached.

HOW DOES IT WORK? Next.js builds a cache identity from the function's arguments plus the "root parameters" of the route (things like tenant, locale, site). Same identity → same saved result.

SIMPLE EXAMPLE:

async function getProducts(category) { 'use cache'; return db.products.find({ category }); }

First visitor to /shop/shoes hits MongoDB. Everyone after that gets the saved array instantly.

WHERE IT WENT WRONG: All seven CVEs are variations of "the cache identity was computed incompletely." Nested cached functions, binary arguments like Blob, calls routed through unstable_cache — in each case something that should have been part of the identity wasn't.

WHY SHOULD A NEXT.JS DEVELOPER CARE? Two reasons. The obvious one: patch. The deeper one: when you enable caching on anything that returns user-specific or tenant-specific data, you are one mistake away from a data breach. Ask yourself every time: "Is every input that changes this output part of the cache key?"

WHAT EXISTING CONCEPT DOES IT REPLACE? Implicit fetch caching and unstable_cache.

SHOULD I LEARN IT? HOW DEEPLY? Yes — LEARN DEEPLY. This is core Next.js 16 knowledge and it shows up in interviews.

🏗️ TODAY'S SYSTEM DESIGN CONCEPT

CONCEPT: Cache Key Design (and cache poisoning)

IN ONE SENTENCE: A cached result must be labelled with every single input that could change it — otherwise you will eventually hand the wrong answer to the wrong person.

WHAT PROBLEM DOES IT SOLVE? Caching makes things fast by reusing work. The entire correctness of a cache rests on one question: "is this request really the same as the one I already answered?" The key is how you answer that question.

SIMPLE REAL-WORLD EXAMPLE: A pharmacy keeps pre-filled prescription bags on a shelf, labelled by surname only. Two customers named "Khan" walk in. One gets the other's medication. The shelf (cache) worked perfectly — the label was wrong. That is exactly the Next.js bug, and exactly what will happen in your Express app if you cache by user name instead of user ID.

HOW IT WORKS: On a request, you compute a key, e.g. products:category=shoes:currency=PKR:v2. You check the cache for that key. Hit → return it. Miss → do the real work, store it under that key, return it.

Three rules that cover 90% of real bugs:

  1. Every input goes in the key. User ID, tenant ID, locale, currency, feature flags, auth role. If it changes the output, it belongs in the label.
  2. Never cache authenticated, user-specific data in a shared cache unless the user ID is in the key. Public data and private data should not live in the same namespace.
  3. Version your keys. Add :v2 to the key. When your data shape changes, bump to :v3 — instant safe invalidation with no cache flush.

WHERE IS IT USED? CDNs (Cloudflare), Redis, HTTP Cache-Control + Vary headers, Next.js, GraphQL clients, browser caches. Everywhere.

HOW WOULD I USE IT WITH NODE / EXPRESS / MONGODB?

Middleware sketch (conceptual):

const key = `dash:v1:tenant=${req.user.tenantId}:user=${req.user.id}:range=${req.query.range}`;
const hit = await redis.get(key); if (hit) return res.json(JSON.parse(hit));
const data = await buildDashboard(req.user); await redis.set(key, JSON.stringify(data), 'EX', 60); res.json(data);

Notice the four things in the key: version, tenant, user, query param. Drop any one and you've built today's CVE yourself.

TERM: Cache poisoning

SIMPLE MEANING: An attacker deliberately gets a bad or attacker-chosen response stored in the cache, so it is then served to many innocent users.

REAL-WORLD EXAMPLE: One of today's Next.js bugs: a crafted URL caused request-specific values to be stored in a shared page shell, so other URLs got wrong content or permanent 404s.

WHY IT MATTERS: One attacker request can damage thousands of user sessions. It's a force multiplier.

WHY IT MATTERS TO ME: If you cache anything derived from a request header, query param or hostname, you need to know this term.

COMMON MISTAKE: Caching on the server with a key based on the URL only — while the response actually varies by the Authorization header. The URL is identical for every user; the response is not. Classic, catastrophic, and extremely common.

WHAT I SHOULD BUILD TO LEARN IT: Small Express + Redis + MongoDB app with a /dashboard endpoint. Deliberately build it with a bad key (URL only). Log in as two users, watch User B see User A's data. Then fix the key and watch it work. Seeing the bug happen on your own machine teaches it permanently.

DIFFICULTY: Intermediate (the concept is beginner-level; the failure modes are not)

WHAT IS IT?

TERM: TSL (Three.js Shading Language)

SIMPLE MEANING: A shader is a tiny program that runs on your graphics card to decide the colour of every pixel. Traditionally you wrote shaders in GLSL — a separate C-like language embedded in your JS as a string. TSL lets you build the same GPU logic by composing JavaScript function calls instead.

REAL-WORLD EXAMPLE: mix(color('#82dbc5'), color('#fbb03b'), sin(time.add(positionLocal.y.mul(4))).mul(0.5)) — that's a real animated gradient material, written in plain JS, no GLSL string.

WHY IT MATTERS: Three.js compiles TSL to WGSL on WebGPU or GLSL on the WebGL2 fallback. One source, both backends. You stop writing two versions.

WHY IT MATTERS TO ME: You already know JavaScript. TSL turns shader work from "learn a new language" into "learn a new API". It is the single lowest-friction on-ramp into shader programming for a JS developer — and the Three.js project is clearly committing its engineering effort there.

🛡️ CYBERSECURITY

The GitHub Actions credential-stealing campaign

WHAT HAPPENED? From 10 November 12:45 UTC, 4,837 compromised GitHub accounts opened probe pull requests across 61,764 repositories. Where the account had collaborator or org permissions, a credential-harvesting workflow was deployed. Aikido confirmed execution in at least 1,806 repos; SafeDep counted 8,093 repos with malicious commits (7,309 workflow injections and 771 npm postinstall hooks). (CONFIRMED — Aikido and SafeDep research; attribution unclear, overlaps with October's GhostAction wave.)

WHAT IS THE VULNERABILITY? It isn't one bug — it's trust. Your CI pipeline holds every secret your app needs. Anyone who can get code to run in it gets everything.

HOW DOES THE ATTACK WORK? (defensive view) The payload grabs Actions secrets, GITHUB_TOKEN, OIDC tokens, cloud credential files and AI-provider API keys. The nasty part is the persistence: it exchanges OIDC tokens for real AWS/GCP/Azure sessions, then modifies the AWS role trust policy to "Principal": {"AWS": "*"}" and adds federated credentials in Entra. Translation: rotating your keys afterwards does not remove the attacker. Finally it reverts the commit and deletes the workflow run to hide the evidence.

TERM: OIDC token (in CI)

SIMPLE MEANING: Instead of storing a permanent AWS key in GitHub, modern setups have GitHub hand your workflow a short-lived identity token, which AWS exchanges for temporary credentials. It's the recommended, more secure pattern.

WHY IT MATTERS: Short-lived credentials limit damage — but only if the attacker can't change who is trusted. This campaign attacked the trust policy itself. The lesson: good security practice is not the same as good security monitoring.

WHO IS AFFECTED? Anyone with a GitHub repo running Actions — including private ones, via compromised collaborator accounts.

TERM: pull_request_target

SIMPLE MEANING: A GitHub Actions trigger that runs a workflow with your repository's secrets when someone opens a pull request from a fork. Normal pull_request runs without secrets — much safer.

REAL-WORLD EXAMPLE: A maintainer wants a bot to auto-label PRs from strangers. Labelling needs write permission, so they use pull_request_target. If that workflow then checks out and runs the stranger's code, the stranger's code runs with full repo secrets. This is called a "Pwn Request". It's how TanStack, PostHog and Nx were compromised.

WHY IT MATTERS TO ME: It's the clearest example of the most important security principle in your work: never let untrusted input execute in a trusted context. Same principle as SQL injection, XSS, and prompt injection in AI agents. One idea, four different costumes.

HOW DO I PROTECT MY APPLICATION?

  1. Set default GITHUB_TOKEN permissions to read-only (Settings → Actions → General). Grant write per-job only where needed.
  2. Audit who has write access to your repos. Remove stale collaborators.
  3. Pin third-party actions to a full commit SHA, not @v3.
  4. Never checkout fork code inside a pull_request_target workflow.
  5. Rotate long-lived tokens. Prefer OIDC — but also alert on changes to cloud IAM trust policies.
  6. Delay installing brand-new package versions. One team's "wait 7 days" policy was widely discussed this week — not a complete defence, but it buys time for researchers to spot a compromise.

WHAT SHOULD I LEARN? Least privilege in CI. Secret rotation. The difference between pull_request and pull_request_target.

SAFE PRACTICAL LAB: Create a throwaway public repo. Add a workflow that prints ${{ github.event.pull_request.title }} into a shell command. Open a PR from a second account with the title test"; echo INJECTED; #. Watch your own log print INJECTED. That's script injection in CI, demonstrated on your own repo in ten minutes, harming nobody. Then fix it by passing the title through an env: variable instead of string interpolation. Delete the repo afterwards.

Supply chain: the bee-js incident is the one to understand

WHAT HAPPENED? On 9 November, attackers with stolen Ethersphere CI credentials published @ethersphere/bee-js@13.3.0 to npm — with valid SLSA provenance — and a trojanized Swarm Desktop build on GitHub, signed and Apple-notarized under the project's own Developer ID. npm pulled the package in ~75 minutes. The desktop build stayed up, served by the auto-updater, for ~8.5 hours. (CONFIRMED — Socket, GHSA-hh7j-5m3j-23pf, maintainer statement.)

TERM: SLSA provenance

SIMPLE MEANING: A cryptographic receipt saying "this package was built by this pipeline from this source commit." It's meant to prove a package wasn't tampered with after building.

WHY IT MATTERS: Here's the uncomfortable lesson — provenance proves where a package was built, not that it's safe. The attacker used the project's real pipeline, so the receipt was genuine. Same with the Apple notarization.

WHY IT MATTERS TO ME: A lot of security advice boils down to "look for the verified badge." This incident shows badges verify process, not intent. Your actual defences are: fewer dependencies, lockfiles, delayed upgrades, and least-privilege tokens.

The clever technical detail worth knowing: the attacker changed one line in package.json — "prepare" → "postinstall". prepare runs when the maintainer builds. postinstall runs on your machine when you npm install, whether or not you ever import the library. One word, total compromise. Note also: npm 12 (July 2026) blocks dependency install scripts unless allow-listed; pnpm 10 and Bun block them by default. npm 11 and earlier do not. Check your npm version.

LEARN THIS #1 — Cache key design

WHAT IS IT? The rule that a cached answer must be labelled with every input that can change it.

WHY NOW? Seven CVEs landed in your own framework for exactly this reason, two weeks ago. The lesson is sitting right there with real examples.

LEARN THIS #2 — Model routing (cheap worker / expensive planner)

WHAT IS IT? Sending each step of an AI task to the cheapest model that can handle it, instead of running everything on your best model.

WHY NOW? Google shipped Carbon and Hydrogen days apart specifically to enable this, and reported ~24% quota savings with Orchestrator. The whole industry is converging on it.

WHY ME? It's a routing problem, which is a backend problem, which is your strength. It costs almost nothing to learn and makes any AI side project you build noticeably cheaper.

WHAT EXACTLY SHOULD I LEARN? Classifying tasks as simple vs complex; calling two different model endpoints from one Node service; logging tokens and cost per request.

WHAT SHOULD I NOT WORRY ABOUT YET? Fine-tuning, embeddings, vector databases, model internals. None of that is needed here.

TIME: 1 hour to understand, 2 hours to build

FREE RESOURCE: Provider docs for whichever API you already have access to.

PRACTICAL MINI PROJECT: POST /ask in Express. If the prompt is under N tokens and contains no "plan/design/analyse" keyword → cheap model. Otherwise → expensive model. Return the answer plus which model was used and the estimated cost. Measure the saving across 20 requests.

🔮 WHERE TECHNOLOGY IS GOING

TREND 1: AI agents are becoming a backend infrastructure category.
WHAT THAT MEANS: Uber's MCP Gateway, MCP's stable release schedule, Edera's work on isolating credentials from agent workloads, GitLab making its MCP server GA — these are not AI research stories. They are gateway, identity and governance stories.
WHY IT MATTERS: The scarce skill is shifting from "can you prompt a model" to "can you give an agent a scoped identity, a tool registry and an audit trail."
WHAT I SHOULD LEARN: MCP, tool schemas, per-tool authorization, gateways, queues, observability.

TREND 2: The supply chain is now the main attack surface for web developers.
WHAT THAT MEANS: This week alone: 4,837 hijacked GitHub accounts, a malicious npm release with valid provenance and Apple notarization, 10 hijacked packages running without install scripts, a pnpm flaw that bypasses --ignore-scripts, and GitHub blocking a trigger by default. Note the direction — attackers are routing around each defence as it appears.
WHY IT MATTERS: Nobody is going to hack your Express route. They'll hack a package you depend on, or your CI.
WHAT I SHOULD LEARN: Dependency minimisation, lockfiles, least-privilege CI tokens, secret rotation, delayed upgrades.

TREND 3: JavaScript runtimes are absorbing userland utilities.
WHAT THAT MEANS: Node added debounce, throttle, PKCS#12 parsing, fs.glob, a net/promises API. Things you used to install, you now import.
WHY IT MATTERS: Partly competition with Bun and Deno, partly a direct response to supply-chain risk. Every removed dependency is one less thing that can be hijacked.
WHAT I SHOULD LEARN: Get in the habit of checking Node's own docs before npm install.

TREND 4: The browser is becoming a serious GPU platform.
WHAT THAT MEANS: ~80% of Three.js core development going to WebGPU/TSL. Experimental meshlet and visibility-buffer pipelines — techniques from Vulkan and D3D12 — now in a browser library. DOM elements now renderable inside a canvas in Chrome.
WHY IT MATTERS: The ceiling on what a website can look like is rising sharply, and GLSL-string-in-JavaScript is being replaced by a JS-native node system. The entry barrier for JS developers is falling.
WHAT I SHOULD LEARN: TSL first. WebGPU compute later.

TREND 5: Streaming is becoming the default way to render the web.
WHAT THAT MEANS: X rebuilt one of the world's biggest React apps around streaming SSR with Suspense and got a profile's first post from 23.9s to 2.7s on slow connections. One server now serves users, crawlers and link-preview bots, shaping the response per audience.
WHY IT MATTERS: For users in Pakistan, India, Africa, Latin America — most of the world's growth — this is the difference between a usable site and an abandoned one. And they did it with five engineers in six months, with agents helping port old behaviour. Small teams can now attempt things that used to need large ones.
WHAT I SHOULD LEARN: Where to place Suspense boundaries, streaming SSR, and what actually blocks hydration.
