🔥 BIGGEST DEVELOPMENTS

1. MCP goes stateless — the biggest protocol revision since launch

WHAT HAPPENED: The 2026-07-28 MCP spec removed protocol-level sessions entirely. Six separate proposals combined to do it. Method and tool names now travel in HTTP headers (Mcp-Method, Mcp-Name) so gateways can route and rate-limit without parsing JSON bodies. Tool list responses now carry ttlMs and cacheScope — literally HTTP-style cache hints. Roots, Sampling and Logging are deprecated with a 12-month window. Dynamic Client Registration is deprecated in favour of Client ID Metadata Documents. (CONFIRMED)

WHAT IS THE TECHNOLOGY?

TERM: Stateless vs stateful protocol / sticky sessions
SIMPLE MEANING: Stateful means the server remembers you between requests, so every one of your requests must come back to the same server instance (a "sticky session"). Stateless means each request carries everything it needs, so any server instance can handle it.
REAL-WORLD EXAMPLE: A JWT is stateless auth — the token carries the identity. A server-side session stored in memory is stateful — if the load balancer sends you to a different container, you are logged out.
WHY IT MATTERS: Stateless services scale horizontally for free. Stateful ones need sticky routing or a shared session store (Redis), which is extra infrastructure and a failure point.
WHY IT MATTERS TO ME: This is the exact same lesson you need for your own Express APIs, and it is today's system design concept.
WHAT I SHOULD DO: Learn deeply. This concept pays off in every backend interview.

TERM: MRTR (Multi Round-Trip Requests)
SIMPLE MEANING: A way for a tool to ask the user a question mid-call without holding a connection open. The server replies resultType: "input_required" with the questions; the client then retries the same call with the answers attached.
REAL-WORLD EXAMPLE: An agent calls deleteCustomer. Instead of a live prompt over an open socket, the server returns "I need confirmation", and the client re-sends the call with confirmed: true.
WHY IT MATTERS: Long-lived open streams break behind load balancers, proxies and serverless. Retry-with-answers works on ordinary HTTP.
WHY IT MATTERS TO ME: This is a pattern you can steal for your own APIs — any multi-step form or confirmation flow. It is also how human-in-the-loop approval works in agents, which is a real product requirement.
WHAT I SHOULD DO: Learn it while building your MCP server.

WHY DOES IT MATTER? MCP is becoming boring infrastructure — and boring is when something gets adopted everywhere. It now runs on the same HTTP plumbing companies already own.

RELEVANCE: 🟢 DIRECT · LEARNING PRIORITY: 🔥 HIGH · MODE: LEARN DEEPLY
WHAT SHOULD I LEARN? The MCP TypeScript SDK (v2.x), the 2026-07-28 spec, tool schemas (now full JSON Schema 2020-12), and MCP OAuth basics.

🤖 AI & AI AGENTS

Deep dive: agent memory (the thing everyone is suddenly building)

WHAT IS IT? A storage layer that lets an agent remember facts, decisions and history across separate sessions. Not the model's context window — an external store the agent reads from and writes to.

WHAT PROBLEM DOES IT SOLVE? The "goldfish problem". A model's context window is wiped every conversation. Without memory, your agent re-asks the same questions, repeats the same mistakes, and cannot be held accountable for past decisions.

HOW DOES IT WORK? (simplified) Three layers, which you can build in MongoDB:

  1. Raw log — every message, tool call and result, appended. Cheap, complete, unusable directly (too big for a context window).
  2. Summaries — periodically compress old history into short facts ("user prefers Roman Urdu", "project uses Next.js 16").
  3. Retrieval — at the start of each turn, fetch only the relevant facts and inject them into the prompt.

The newer projects add a fourth idea worth stealing: causal links — storing why a decision was made and what it depended on, so you can trace any action back to its cause. That is an audit log, and it is a normal backend design problem.

TERM: Vector database / embedding
SIMPLE MEANING: An embedding turns text into a list of numbers that captures its meaning. A vector database finds stored text whose numbers are closest to your query's numbers — i.e. search by meaning instead of by exact keyword.
REAL-WORLD EXAMPLE: You search "how do I cancel" and it finds a document titled "Refund and termination policy" even though no word matches.
WHY IT MATTERS: It is how AI apps look things up in your own data.
WHY IT MATTERS TO ME: You do not need a new database. MongoDB Atlas has vector search built in. You can build a full memory system inside the database you already know.
WHAT I SHOULD DO: Build it. This is the single highest-leverage AI project for a MERN developer.

WHY ARE PEOPLE USING IT? Because stateless chatbots are a demo and stateful agents are a product.

HOW COULD I USE IT IN A REAL PROJECT? A support agent for a MERN app: Express endpoint → agent loop → tools that query MongoDB → a memories collection with Atlas Vector Search → summariser job on a queue.

DO I NEED TO LEARN THIS NOW? Yes. It is the part of AI that is genuinely backend work.

RELEVANCE: 🟢 DIRECT · LEARNING PRIORITY: 🔥 HIGH · MODE: LEARN DEEPLY

Deep dive: agent orchestration (what google/ax and friends actually are)

WHAT IS IT? The runtime that executes an agent's plan: which step runs next, what happens on failure, how many things run in parallel, how state is persisted, how tools are permitted.

WHAT PROBLEM DOES IT SOLVE? A naive agent is a while loop calling an LLM. That loop breaks in production: it hangs, loops forever, blows the budget, loses work on a crash, or calls a destructive tool it should not have.

HOW DOES IT WORK? It looks exactly like a job system you would design in Node:

  • Each step is a durable task with an ID, stored so a crash does not lose it.
  • Steps run through a queue with concurrency limits and retries with backoff.
  • Tools are declared with schemas and permissions.
  • Every step is traced for observability and cost.
  • Human approval is a first-class state, not a hack.

TERM: Capability scoping (least privilege for agents)
SIMPLE MEANING: Give an agent only the tools and permissions it actually needs for its job.
REAL-WORLD EXAMPLE: A "summarise customer feedback" agent should have readFeedback and nothing else. It should physically not be able to call deleteCustomer.
WHY IT MATTERS: A model can be talked into things. Permissions cannot. The only reliable defence against a manipulated agent is not giving it the dangerous tool.
WHY IT MATTERS TO ME: This is authorisation — you already do this with JWT roles and Express middleware. The same middleware pattern applies to tool calls.
WHAT I SHOULD DO: Build your MCP server with per-tool permission checks from day one.

WHY DOES IT MATTER TO ME? Read this list again: queues, retries, idempotency, observability, authorisation. Every item is a backend skill you are already trying to learn. Agent orchestration is not a new discipline — it is distributed systems with an LLM in one of the boxes. That is your unfair advantage.

RELEVANCE: 🟢 DIRECT · LEARNING PRIORITY: 🔥 HIGH · MODE: LEARN DEEPLY

Transferable lesson, not a science lesson

Why am I telling you this? AI research keeps producing results in biology, chemistry and safety research. Almost none of it belongs in your learning plan. What is worth extracting is the architecture. The recurring pattern in large AI research systems: one big problem is split across many parallel AI workers, each result is verified, and results are merged. That is fan-out/fan-in with a verification stage — and it is the same shape as a production AI pipeline you might build (e.g. "run 1,000 product descriptions through an LLM, validate each against a schema, retry failures, merge"). Learn the architecture. Ignore the science.

💻 MERN / JAVASCRIPT / WEB

Next.js Cache Components — the caching model you will actually have to learn

WHAT CHANGED? Next.js 16 (current docs show 16.3.4) makes caching explicit and opt-in. The old implicit automatic caching of the App Router — the thing that confused everybody in Next 13-15 — is gone. Experimental PPR as a separate flag is gone too; it is now folded into Cache Components. (CONFIRMED — nextjs.org docs and blog)

WHAT IS IT?

TERM: Cache Components / "use cache"
SIMPLE MEANING: A directive you put at the top of a page, component or function to say "cache the result of this". Everything else is dynamic by default. The compiler generates the cache key for you from the function's arguments.
REAL-WORLD EXAMPLE:

// next.config.ts
export default { cacheComponents: true }

// app/page.tsx
import { cacheLife, cacheTag } from 'next/cache'

async function ProductList() {
  'use cache'
  cacheLife('hours')      // how long it stays fresh
  cacheTag('products')    // label for invalidation
  const products = await db.collection('products').find().toArray()
  return <ul>{products.map(p => <li key={p._id}>{p.name}</li>)}</ul>
}

export default function Page() {
  return (
    <>
      <ProductList />                       {/* cached */}
      <Suspense fallback={<Spinner />}>
        <CartSummary />                     {/* dynamic, streams in */}
      </Suspense>
    </>
  )
}

When a product changes, your API route calls revalidateTag('products', 'hours') or the newer updateTag().

WHY WAS IT CREATED? Because in Next 13-15, developers could not predict whether a page was cached. The framework cached aggressively and invisibly, and "why is my data stale in production but fine locally?" became the most common Next.js complaint. Making it explicit fixes the mental model.

HOW DOES IT WORK? Next renders a static HTML shell immediately, then streams the dynamic parts in as they resolve. One page can be part-static, part-cached-dynamic, part-live. That is Partial Pre-Rendering.

TERM: PPR (Partial Pre-Rendering)
SIMPLE MEANING: Serving the unchanging parts of a page instantly from a cache while the personalised parts load in afterwards, in one request.
REAL-WORLD EXAMPLE: An e-commerce page where the product grid is instant but "Your cart (3)" fills in a moment later.
WHY IT MATTERS: Before PPR, a page was either fully static (fast, but can't be personalised) or fully dynamic (personalised, but slow). PPR removes the choice.
WHY IT MATTERS TO ME: This is the core performance feature of the framework you build in. Interviewers will ask about it.
WHAT I SHOULD DO: Learn deeply — it is directly your stack.

WHAT EXISTING CONCEPT DOES IT REPLACE? ISR + route segment configs (revalidate, dynamic = 'force-static') + the implicit fetch cache + the experimental PPR flag — all collapsed into one mechanism.

Two gotchas worth knowing now:

  • Cache Components requires the Node.js runtime. Routes with runtime = 'edge' must be migrated.
  • With it enabled, Next uses React's <Activity> to keep the old route mounted but hidden during navigation instead of unmounting it. Your dropdowns, dialogs and cleanup effects may behave differently. Read the "Preserving UI state" guide before upgrading a real app.

SHOULD I LEARN IT? HOW DEEPLY? Yes — LEARN DEEPLY. 🟢 DIRECT · 🔥 HIGH. Learn: use cache, cacheLife, cacheTag, revalidateTag vs updateTag, and where <Suspense> boundaries are mandatory.

Also on your radar this week

WHAT IT REPLACES: manual memoisation. 🟢 DIRECT · 🟠 MEDIUM · UNDERSTAND THE BASICS — turn it on in a side project and watch the re-render count drop.
  • Next.js Devtools MCP ships in 16 — it exposes your app's routing and caching semantics to an AI agent so the agent can debug Next-specific behaviour without you explaining the framework. Note the pattern: frameworks are now shipping MCP servers for themselves. 🟢 DIRECT · 🟠 MEDIUM · EXPERIMENT.

🏗️ TODAY'S SYSTEM DESIGN CONCEPT

CONCEPT: Stateless services and horizontal scaling (and why sticky sessions are a trap)

IN ONE SENTENCE: If every request carries everything the server needs to handle it, you can run as many identical copies of your server as you like and any of them can answer any request.

WHY TODAY? Because MCP just did exactly this, deliberately, as its biggest-ever change — and their stated reason was "so any request can land on any instance behind a plain round-robin load balancer". That is the cleanest real-world justification of this concept you will ever get.

WHAT PROBLEM DOES IT SOLVE? One server instance eventually runs out of CPU/RAM. You want to run five. But if instance #1 is holding your session in memory, the load balancer must always send you back to instance #1 (a "sticky session"). Now: if #1 dies, you lose everything; you cannot scale to zero; deploys drop connections; and autoscaling barely helps because load is unevenly pinned.

SIMPLE REAL-WORLD EXAMPLE: A hotel. Stateful: only the receptionist who checked you in remembers you — if she goes on break, you are stuck. Stateless: you carry a key card with your room number on it, so any receptionist can help you.

HOW IT WORKS:

  1. Move per-user state out of process memory. Either into the request itself (a signed token) or into a shared store (Redis/MongoDB) that all instances read.
  2. Keep handlers pure with respect to instance-local state: no module-level mutable maps holding user data, no in-memory upload buffers, no local file writes you expect to read back later.
  3. Let the load balancer do plain round-robin. No sticky cookies.
  4. For long-running work, return a handle (a job ID) instead of holding the connection. The client polls or subscribes. MCP did exactly this with its Tasks extension: tasks/get polling replaced a blocking call.

WHERE IS IT USED? Every serverless platform (Vercel, Lambda, Cloudflare Workers) forces this on you. JWT auth exists because of it. REST's "stateless" constraint is this. Kubernetes autoscaling depends on it.

HOW WOULD I USE IT WITH NODE / EXPRESS / MONGODB?

  • ❌ const sessions = new Map() at module scope → breaks with 2+ instances.
  • ❌ express-session with the default MemoryStore → same problem.
  • ✅ JWT in an httpOnly cookie, verified per request — nothing stored server-side.
  • ✅ Or connect-mongo / Redis as the session store — state is shared, so instances stay interchangeable.
  • ✅ Rate limiting: an in-memory counter is wrong with 5 instances (each allows the full quota, so you allow 5x). Use a Redis counter.
  • ✅ File uploads: stream to S3/cloud storage, not local disk.
  • ✅ WebSockets are inherently sticky — when you need them across instances, use a shared pub/sub adapter (e.g. Redis) so a message published on instance #2 reaches a socket held by instance #4.

COMMON MISTAKE: Believing you are stateless because you use JWTs, while a rate limiter, a cache, a WebSocket map, or an in-memory job queue quietly holds per-instance state. It works perfectly on one instance and fails mysteriously the moment you scale. The bug always looks like "it works sometimes".

SECOND COMMON MISTAKE: Going stateless but forgetting idempotency. If a request can land on any instance and clients retry on failure, the same "create payment" call can execute twice. Fix: an Idempotency-Key header stored with a unique index in MongoDB; if the key exists, return the stored result instead of re-running.

WHAT I SHOULD BUILD TO LEARN IT: Take an existing Express app using express-session with MemoryStore. Run three instances behind a simple round-robin proxy (nginx, or a 20-line Node proxy). Watch logins randomly fail. Then fix it three ways — JWT, Mongo session store, Redis session store — and add a Redis-backed rate limiter. You will never forget the lesson.

DIFFICULTY: Intermediate

🎨 CREATIVE DEVELOPMENT

TSL — stop learning GLSL first, learn this

WHAT IS IT?

TERM: TSL (Three Shading Language)
SIMPLE MEANING: A way to write shader logic in JavaScript, by composing small "nodes" (values and operations) instead of writing shader source code as a string. Three.js then compiles your JavaScript into the real shader language the browser needs — WGSL for WebGPU, or GLSL for WebGL.
REAL-WORLD EXAMPLE: Instead of a template-string GLSL fragment shader, you write something like color.mul(sin(time.mul(2))).add(0.2) in JS. Autocomplete works. Type errors surface in your editor. You can extract a glow effect into a reusable function and import it.
WHY IT MATTERS: Shaders used to be opaque strings with no tooling — no autocomplete, no type checking, no imports, and you had to write two versions if you supported both WebGL and WebGPU. TSL kills all four problems and writes once, runs on both.
WHY IT MATTERS TO ME: You are a JavaScript/TypeScript developer. TSL turns shader programming from "learn a foreign C-like language" into "compose functions in the language you already write every day". It is the single biggest lowering of the barrier into serious creative development for someone with your background.
WHAT I SHOULD DO: Learn it — and make it your default instead of ShaderMaterial + GLSL.

WHY IS IT BECOMING IMPORTANT NOW? Three concrete things converged:

  1. Browser coverage crossed the line. With Safari 26 shipping WebGPU, roughly 95% of users can run WebGPU, and Three.js falls back to WebGL 2 automatically for the rest. You no longer ship WebGPU "for fun".
  2. TSL got fast. A merged PR improved TSL compilation performance ~3x (one scene went from ~1,550ms to ~515ms of material compilation) mostly by caching node type resolution. Compile stutter was a real reason people avoided it.
  3. There is now a migration path. A WebGLRenderer NodeMaterial compatibility layer lets you use TSL/NodeMaterials on the old renderer (renderer.setNodesHandler(new WebGLNodesHandler())), so you can port materials gradually and swap to WebGPURenderer later. It targets ~90% of cases, with known limits (VSM shadows, MRT nodes, storage textures, transmissive materials, some instancing/skinning edge cases).

The hard constraint you must know: WebGPURenderer does not support ShaderMaterial, RawShaderMaterial, or onBeforeCompile() hacks. Nor does it support EffectComposer — it has its own node-based post-processing stack (with new effects like SSGI, SSS, better DoF available only there). So every GLSL shader tutorial you follow today is code you will have to rewrite. (CONFIRMED — threejs.org WebGPURenderer manual)

WHAT CAN IT DO / WHAT CAN I BUILD? Three.js r185 landed a compute-shader-based rasterizer (Nanite-style) and full WebGPU skinning with instancing.

TERM: Compute shader / GPU compute
SIMPLE MEANING: Using the GPU for general parallel maths, not just drawing pixels. Thousands of tiny calculations run simultaneously.
REAL-WORLD EXAMPLE: 500,000 particles each needing position updates every frame. On the CPU in JS: impossible at 60fps. On a compute shader: routine.
WHY IT MATTERS: It is the difference between "a few thousand animated things" and "a million". This capability simply did not exist in WebGL.
WHY IT MATTERS TO ME: This is what separates an Awwwards site-of-the-day from a nice portfolio. Big particle systems, GPU physics, crowds, flow fields.
WHAT I SHOULD DO: Learn TSL basics first, then one GPU compute particle example. Do not start with the rasterizer — that is deep water.

WHAT SHOULD I LEARN FIRST? In this order: (1) React Three Fiber with WebGPURenderer instead of the default — get it rendering at all; (2) TSL fundamentals — uniform, attribute, vec3, time, maths node chaining, colorNode and positionNode on a MeshBasicNodeMaterial; (3) one TSL vertex displacement effect (wave a plane); (4) TSL post-processing; (5) only then compute shaders. Skip raw GLSL entirely unless you must maintain old code.

RELEVANCE: 🟢 DIRECT · LEARNING PRIORITY: 🔥 HIGH · MODE: LEARN DEEPLY

Reference point for what's achievable: a community showcase this year ran 4,000 particles with custom magnetic/cursor physics and all shading in TSL — additive glow, radial falloff, pulsing emission, per-instance colours — on React 19 + R3F + Three r183 + WebGPU + Zustand + Vite. That is a realistic target project for you, not a research demo.

🛡️ CYBERSECURITY

The GHAPPIER npm loader — and why "signed package" is not "safe package"

WHAT HAPPENED? Covered above in the top stories. Recapping the security mechanics, because they are the lesson: attacker had push access to main on the repo behind @dforge-core/dforge-mcp. They edited the GitHub Actions workflow so any push to main triggered a release, then rewrote it 14 minutes later so it could publish unattended. The payload was one line at line 3320 of a 99KB file. It opened a four-stage chain ending in a remote shell that deleted itself from disk as it ran. It triggered only when the MCP server was started, not on install. A related variant pulled its commands from Ethereum transactions instead of a domain or IP. CloudSEK traced the loader family across 65 repositories, 73 infected files, 22 accounts. CloudSEK's own summary: "Every action in this report is an authorised action taken with a stolen key." (CONFIRMED — CloudSEK, 20 Sep 2026; no CVE issued at time of reporting)

WHAT IS THE VULNERABILITY? There isn't a software bug to patch. The weakness is trust design:

TERM: Provenance attestation (and its limit)
SIMPLE MEANING: A signed record proving which CI system built a package from which commit. It proves the origin of the build, not the honesty of the code.
REAL-WORLD EXAMPLE: A sealed envelope from a trusted courier. The seal proves nobody tampered in transit. It says nothing about whether the sender wrote something malicious inside.
WHY IT MATTERS: Under trusted publishing, npm trusts the repo's CI identity — so push access became publish access. No npm token needed to be stolen. And npm audit signatures passes cleanly on a malicious release.
WHY IT MATTERS TO ME: Do not treat a provenance badge as a safety signal. It is an authenticity signal.
WHAT I SHOULD DO: Learn defence in depth below.

TERM: Blockchain C2 (command and control)
SIMPLE MEANING: The malware reads its instructions from data embedded in cryptocurrency transactions instead of contacting a server.
REAL-WORLD EXAMPLE: Normally defenders block the malware's domain and it dies. Here there is no domain to block and no takedown to file — the ledger is public and permanent.
WHY IT MATTERS: Traditional blocklist defences stop working. Detection has to move to behaviour (unexpected outbound connections, unexpected child processes).
WHY IT MATTERS TO ME: Mostly awareness — but it explains why "just block the bad domain" is no longer the answer, and why egress control matters.
WHAT I SHOULD DO: Understand the basics. Nothing to implement personally.

HOW DOES THE ATTACK WORK (defensive view)? Compromise a developer machine → steal a token or extension-level access → gain push rights to a package repo → make CI publish for you → ship a tiny loader that only activates on run, not install → self-delete to defeat file-based forensics. Note that every step used a legitimate, authorised mechanism.

WHO IS AFFECTED? Anyone who installed @dforge-core/dforge-mcp@0.2.21 and started its server. Separately, anyone who installed the malicious @tanstack/* versions from 11 May 2026 should assume credential theft.

WHY SHOULD A MERN DEVELOPER CARE? Your entire toolchain is npm. The TanStack vector hit mainstream React packages. The dforge vector hit an MCP package — precisely the category you are about to start installing. Your laptop holds GitHub tokens, SSH keys, .env files with Mongo URIs, Railway tokens and AI API keys. A dependency that runs code on your machine has all of it.

HOW DO I PROTECT MY APPLICATION? Concretely, today:

  1. Commit your lockfile and use npm ci, never npm install, in CI. npm ci installs exactly the locked versions. npm install can drift you onto a fresh malicious release.
  2. Add ignore-scripts=true to your .npmrc and run npm rebuild deliberately for the few packages that genuinely need native builds. Most install-time malware runs in postinstall.
  3. Delay adoption of brand-new versions. Both attacks here lived for ~35 minutes and were then withdrawn. A 24-72 hour cooldown before upgrading dependencies would have protected you completely, for free.
  4. Scope your tokens. A GitHub fine-grained PAT that can read one repo is worth far less to an attacker than a classic token with full org access. Set expiry dates.
  5. Get secrets off your dev machine's plaintext. Use a secret manager or at minimum never keep production .env files on the laptop you install packages on.
  6. Revoke access when people leave. The CrowdSec breach only happened because an ex-employee's token still worked. Make an offboarding checklist even if your "team" is two friends.
  7. In CI, never check out untrusted PR code in a job that holds secrets (the pull_request_target footgun). Pin third-party actions to a full commit SHA, not a tag.
  8. Audit lockfiles for the known-bad versions. Treat any lockfile referencing @dforge-core/dforge-mcp@0.2.21 as a compromise indicator; pin to 0.2.22+. Same for the malicious @tanstack/* versions from 11 May.

WHAT SHOULD I LEARN? Supply-chain security fundamentals: lockfiles, SBOM basics, npm provenance (and its limits), least-privilege tokens, CI secret hygiene, secret rotation.

SAFE PRACTICAL LAB (30 minutes, entirely local, nothing malicious):

  1. Create an empty folder. Make a local package with a postinstall script that just runs console.log("I could have read your SSH keys") and writes a file to your temp dir.
  2. npm install ./that-folder. Watch it execute. That is the entire attack surface, demonstrated.
  3. Add ignore-scripts=true to .npmrc. Reinstall. Watch it not execute.
  4. Run npm ls --all on your biggest project and count your real dependency tree. Then run npm audit signatures and note that a clean result would not have caught GHAPPIER.
  5. Rotate one GitHub token and replace it with a fine-grained, expiring, single-repo token. Do it for real, not as an exercise.

RELEVANCE: 🟢 DIRECT · LEARNING PRIORITY: 🔥 HIGH · MODE: LEARN DEEPLY (this is the cheapest security win available to you)

One MCP-specific security note

The new MCP spec hardened authorisation: clients must now validate the iss parameter on authorisation responses (RFC 9207) to prevent "mix-up" attacks, credentials are bound to the issuer that minted them, and Dynamic Client Registration is deprecated in favour of Client ID Metadata Documents.

TERM: Authorisation-server mix-up attack
SIMPLE MEANING: When one app talks to many different OAuth providers, an attacker can trick the app into redeeming a code issued by provider A at provider B, leaking the code. Checking which issuer actually sent the response (iss) blocks it.
REAL-WORLD EXAMPLE: Your app supports "Login with Google" and "Login with GitHub". Without issuer validation, a malicious flow can cross the wires.
WHY IT MATTERS: MCP's shape — one client, many servers — makes this class of bug much more likely, which is why they hardened it.
WHY IT MATTERS TO ME: You already do auth in MERN apps. If you build multi-provider OAuth, validate iss. 🟢 DIRECT · 🟠 MEDIUM · UNDERSTAND THE BASICS.

  • 0-10: Skim the MCP spec changelog. You are only looking for one thing: every request is self-contained, there is no initialize handshake, no session ID. Do not read the whole spec.
  • 10-20: Install the official TypeScript SDK. Get an empty server running that starts without errors and responds to server/discover.
  • 20-40: Add one tool. Define its input schema ({ query: string }) and output schema. Wire the handler to a real Mongo find().
  • 40-55: Connect a real MCP client to it. Ask it something that forces the tool call. Debug until actual data from your database appears.
  • 55-60: Write three sentences in a file: what surprised you, what you did not understand, what you will add next. That note is what turns an hour of tinkering into a week of direction.
