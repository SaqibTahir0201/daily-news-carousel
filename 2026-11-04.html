1. Next.js shipped a security patch — your app probably needs it today

WHAT HAPPENED:
On 3 November 2026 the Next.js team released 16.4.5 and 15.5.29, fixing six security problems. The worst one (High severity) can leak one customer's cached data to another customer in apps that mix unstable_cache with the newer use cache. This is confirmed on the official Next.js blog, with GitHub advisory IDs.

WHAT IS THIS?
TERM: Cross-tenant cache disclosure.
Simple meaning: "Tenant" = one customer/organisation inside your app. A cache stores a computed result so you don't recompute it. If the cache forgets which tenant the result belonged to, Tenant B can be handed Tenant A's data.
Real-world example: A SaaS dashboard. Company A opens its invoice page. Company B opens the same page one millisecond later. Because the cache filled "cold" at the same moment and didn't check the tenant ID, Company B sees Company A's invoices.
Why it matters: It is a data breach caused by a performance optimisation, not by a hacker breaking in.
Why it matters to you: You build Next.js apps. If any of them has users from different accounts and uses caching, this is literally your bug.

RELEVANCE: 🟢 DIRECT   IMPORTANCE: 🔥 HIGH

WHAT I SHOULD DO: Run npm ls next in every Next.js project today. If below 16.4.5 (or 15.5.29 on the 15 line), upgrade and redeploy. This takes 10 minutes and is the highest-value thing you'll do today.

WHAT HAPPENED:

TERM: APM (Agent Package Manager).
Simple meaning: A package manager — like npm, but for the text you feed an AI agent: its skills, prompts, instructions, chat modes and MCP server configs. You declare them in a manifest, pin exact versions in a lockfile, and share them across repos.

C. The MCP ecosystem is having its security reckoning

WHAT HAPPENED: Three threads converged. (1) The 2026-07-28 MCP spec — the largest revision since launch — made MCP stateless: protocol-level sessions, the Mcp-Session-Id header and the initialize handshake are gone; OAuth 2.1 became first-class; Dynamic Client Registration is deprecated. (2) In late October, CVEs landed in the official MCP Python and TypeScript SDKs (e.g. CVE-2026-116684, CVE-2026-111771) for a missing token audience check — and critically, the fix ships switched off by default, so upgrading alone does not protect you. (3) GitBook told all customers to re-authenticate their MCP servers after its breach. Status: CONFIRMED (spec + GitHub Advisory Database + vendor notice).

WHAT IS THE TECHNOLOGY?
TERM: MCP (Model Context Protocol). Simple meaning: A standard way for an AI app to discover and call external tools — "USB-C for AI tools". You run an MCP server exposing tools; an AI client calls them.
TERM: Stateless protocol. Simple meaning: The server remembers nothing between requests. Every single request must carry everything needed to authenticate and identify itself. Example: a JWT sent on every call, versus a session cookie the server looks up.
TERM: Token audience binding (the aud claim).
Simple meaning: A token should say "I am only valid for service X". Service Y must reject it even though the signature is perfectly valid.
Real-world example: A user has a valid token for your CRM API. Without an audience check, that same token also unlocks your MCP server. The CRM — or anyone who ever receives that token — can now call your tools.
Why it matters: Checking the signature and expiry is not enough. This is the single most commonly skipped JWT check in the industry.
Why it matters to you: You list Authentication and API security as learning goals. This is the highest-value, least-known auth check you can learn this month, and it applies to every JWT you've ever issued — not just MCP.

RELEVANCE: 🟢 DIRECT   LEARNING PRIORITY: 🔥 HIGH

WHAT SHOULD I LEARN? JWT claim validation in depth: iss, aud, exp, nbf, and why "never pass a client's token through to a downstream API" is a hard rule.

🤖 AI & AI AGENTS

One theme dominated today, and it is the theme that matters most to a backend developer. Let me run it through the full filter.

THE AGENT SUPPLY CHAIN

WHAT IS IT?
Until recently, the text you gave an AI agent — its instructions, its skills, its list of allowed tools, its MCP server addresses — lived in a file on your laptop that you edited by hand. As of this week that text is becoming infrastructure: declared in a manifest (apm.yml), pinned in a lockfile (apm.lock.yaml), fetched from remote sources, and auto-updated by Dependabot.

WHAT PROBLEM DOES IT SOLVE?
Prompt sprawl. A 40-engineer team had 40 slightly different versions of the same instruction file, and no way to know which one an agent actually used when it did something wrong.

HOW DOES IT WORK? (simplified)
Exactly like npm. A manifest lists what you depend on. A resolver fetches those Git dependencies. A lockfile records the exact resolved versions so every machine gets byte-identical agent context. Dependabot watches upstream and opens a PR when a version moves.

WHY ARE PEOPLE USING IT? Reproducibility and auditability. If an agent deletes a production table, you need to know precisely which instructions it was running.

WHY DOES IT MATTER TO ME?
Two reasons, and the second is the important one.
1. You already know this model cold. package.json → apm.yml. Nothing new to learn conceptually.
2. Every supply chain gets attacked. npm taught the industry about typosquatting, malicious postinstall scripts and dependency confusion. The agent supply chain is at the pre-attack stage right now — and this week already gave us the preview: the Postman config allegations, a malicious npm MCP package (gadgethumans-mcp) reported sending a wallet private key to a remote server on every tool call, and research showing two working malicious MCP servers passed five different security scanners cleanly.

HOW COULD I USE IT IN A REAL PROJECT?
Concretely: in your Node/Express AI projects, stop putting prompts in string literals. Put them in versioned files, load them at boot, and log the version with every agent run. You get reproducibility now and APM compatibility later for free.

WHAT SHOULD I LEARN? The failure modes, in this order: tool poisoning (a malicious tool description steering the model before any tool is even called — research measured a ~36.5% success rate across 20 model settings, with more capable models often more exposed), rug pulls (a tool that behaves well until it's trusted, then changes), and token passthrough (forwarding a user's token downstream — explicitly forbidden by the MCP spec).

DO I NEED TO LEARN THIS NOW? The security concepts: yes. The APM tooling: no, not yet — it's four days old.

RELEVANCE: 🟢 DIRECT   LEARNING PRIORITY: 🔥 HIGH

A SECOND PATTERN WORTH NAMING: CAPABILITY SCOPING

TERM: Capability scoping (least privilege for agents).
SIMPLE MEANING: Give an agent only the tools and permissions it actually needs for its job — nothing more.
REAL-WORLD EXAMPLE: An agent that summarises support tickets needs readTicket. It does not need deleteTicket, refundCustomer or shell access. If prompt injection convinces it to delete everything, there is simply no tool available to do so.
WHY IT MATTERS: You cannot reliably stop prompt injection with better prompts. Prompt injection is an architecture problem. The fix is removing the capability, not asking the model nicely.
WHY IT MATTERS TO ME: This is the bridge between your two learning tracks. "Which tools does this agent get, under whose identity, with which scopes?" is an Express middleware and authorization question, not an AI question. Your backend skills are the moat here.
WHAT I SHOULD DO: Learn and apply. The industry guidance is a progressive scope model: start with minimal read-only scope, then escalate privilege only when a privileged tool is first called. Wildcard scopes like * or full-access are flagged as the classic mistake.

💻 MERN / JAVASCRIPT / WEB

Next.js caching: what actually changed, and what you must understand

WHAT CHANGED? Six advisories patched in 16.4.5 / 15.5.29. Beyond the high-severity tenant leak, the medium-severity ones are each a small, memorable lesson:

  • Shared shell cache poisoning (self-hosted next start, Cache Components on, Partial Prefetching off): a crafted URL can store request-specific values into a page shell reused by other URLs — causing wrong content or permanent 404s for other users.
  • Cookie exposure via x-middleware-set-cookie: Edge Route Handlers / Edge API routes using NextResponse.cookies.set() can put the serialized cookie into an internal response header. Unlike Set-Cookie, that header is readable by same-origin JavaScript — so an HttpOnly cookie stops being HttpOnly. Node.js Route Handlers and cookies().set() were not affected in the reproduction.
  • SVG rejection bypass in Image Optimization: an image from an allowed source can be misclassified as AVIF and slip past images.dangerouslyAllowSVG: false, reaching the SVG parser you deliberately excluded.
  • Stale compressed response framing: returning an attacker-controlled fetch Response unchanged can send decompressed bytes with the compressed response's framing headers — behind an HTTP/1.1 reverse proxy that pipelines requests on a shared connection, responses can be delivered to the wrong client.

WHAT IS IT? — the concept you need
TERM: Cache Components (and use cache).
Simple meaning: Next.js's current caching model. Instead of a whole page being static or dynamic, you mark individual functions or components with 'use cache' and Next.js caches each piece separately. Next.js 16.4 recommends it for every app, create-next-app enables it, and it is expected to become the default in Next.js 17.
Why it was created: The old model was all-or-nothing. A page with one personalised greeting had to be fully dynamic, throwing away caching for the 95% of the page that was identical for everyone.
How it works (simplified): Each cached unit gets a cache key computed from its inputs. Same key → reuse the stored result. Different key → recompute.
Simple example: A product page. getProduct(id) is cached per product ID and shared by everyone. getCartCount(userId) is never cached. One page, two caching policies.

WHAT EXISTING CONCEPT DOES IT REPLACE? It replaces page-level revalidate / force-dynamic thinking and the older unstable_cache API. And that transition is exactly where this week's High-severity bug lived — in the seam between the old API and the new one, when both are used together.

WHY SHOULD A NEXT.JS DEVELOPER CARE? Because the entire class of bug reduces to one question: "is everything that makes this result different also part of the cache key?" If the tenant ID, the user ID or the locale changes the output but is missing from the key, you will eventually serve one user's data to another. Framework bugs get patched. Your cache-key bugs do not.

SHOULD I LEARN IT? HOW DEEPLY? 🟢 DIRECT, 🔥 HIGH — LEARN DEEPLY. Cache Components is becoming the default; you cannot skip it.

WHAT SHOULD I LEARN? 'use cache', cache keys, cache tags and targeted revalidation, what a "root parameter" is, and why mixing unstable_cache with use cache is now a code smell.

🏗️ TODAY'S SYSTEM DESIGN CONCEPT

CONCEPT:
Cache Key Design & Tenant Isolation

IN ONE SENTENCE:
A cached result must be stored under a key that includes every single input that could change the result — especially who is asking.

WHAT PROBLEM DOES IT SOLVE?
It prevents the most dangerous bug caching can produce: serving the right answer to the wrong person. Note that it's not a performance problem — it's a correctness and privacy problem created by a performance optimisation.

SIMPLE REAL-WORLD EXAMPLE:
A hospital reception desk keeps a tray of prepared files to be fast. A nurse asks for "the blood test results". The receptionist hands over the top file from the tray — it was prepared for a different patient. Fast, and catastrophic. The fix: label every file with the patient ID, and never hand one over without matching the label.

HOW IT WORKS:
Three rules.
1. Key completeness. The key = a hash of every input that affects the output: resource ID + tenant ID + user ID (if the data is personal) + locale + API version + any feature flag that changes the shape.
2. Never cache across a trust boundary. If two callers must not see each other's data, their results must never share a key. The safest approach is prefixing: tenant:{tenantId}:invoice:{id}.
3. Watch the cold-fill race. The subtle failure is two requests arriving while the cache is empty. Request A starts computing; Request B finds an in-flight entry and waits on it; B receives A's result. That is correct behaviour — unless A and B are different tenants. This is precisely the shape of the Next.js High-severity bug. The fix: the in-flight entry must be keyed by the full key, not just the resource.

WHERE IS IT USED?
Everywhere there is a cache: Redis, HTTP Cache-Control and Vary headers, CDN edge caches, framework data caches, React Query, and your own in-memory memoisation.

HOW WOULD I USE IT WITH NODE / EXPRESS / MONGODB?

// ❌ DANGEROUS — key ignores who is asking
const key = `invoices:${page}`;

// ✅ SAFE — tenant is part of the identity of the data
const key = `t:${req.auth.tenantId}:invoices:${page}:v2`;

async function getCached(key, ttl, compute) {
  const hit = await redis.get(key);
  if (hit) return JSON.parse(hit);

  // single-flight lock is ALSO keyed by the full key,
  // so two tenants can never wait on each other's computation
  const result = await singleFlight(key, compute);
  await redis.set(key, JSON.stringify(result), 'EX', ttl);
  return result;
}

Two extra Express-specific notes. First, derive the tenant ID from the verified token in middleware (req.auth.tenantId) — never from a query parameter or header the client controls, or the client picks its own cache namespace. Second, if you cache HTTP responses, any request header that changes the body must be listed in Vary, and responses for logged-in users need Cache-Control: private so no shared proxy stores them.

COMMON MISTAKE:
Building the cache key from the URL alone. The URL /api/invoices?page=1 is identical for every tenant in the system. The thing that distinguishes them lives in the Authorization header, which is invisible to the key. This single mistake has caused more real data leaks than most exotic exploits.

WHAT I SHOULD BUILD TO LEARN IT:
A tiny Express + Redis app with two fake tenants and one cached endpoint. Step 1: build it with the wrong key and fire concurrent requests from both tenants until you watch the data cross over. Step 2: fix the key and prove it never crosses again. Seeing the leak happen on your own machine is worth ten articles.

🎨 CREATIVE DEVELOPMENT

1. Three.js r187 — the WebGPU/TSL migration is no longer optional

WHAT IS IT? Three.js r187 shipped 30 October 2026. An independent line-count analysis of the core found that 79% of changed core lines (14,242 of 17,941) were on the new WebGPU renderer and TSL side, with the same pattern holding at 82% and 79% in the two previous releases. The three/tsl entry point's exported names grew from 638 → 682 → 819. Meanwhile the classic three entry point stayed flat at ~443 exports.

WHAT IS THE TECHNOLOGY?
TERM: WebGPU. Simple meaning: The modern browser graphics API replacing WebGL. It talks to the GPU more directly, is faster, and adds compute shaders — the ability to run general-purpose parallel maths on the GPU, not just drawing. Example: simulating a million particles entirely on the GPU, which WebGL cannot do well.
TERM: TSL (Three.js Shading Language). Simple meaning: You write shader logic as chained JavaScript function calls instead of as GLSL/WGSL strings in another language. Three.js then transpiles it to WGSL (for WebGPU) or GLSL (for WebGL2) depending on the active backend. One codebase, both worlds.
Simple example: Instead of a GLSL string, you write positionLocal.y.mul(6).add(time.mul(2)) then sin() it, and assign that to a material's positionNode. WebGPURenderer uses WebGPU when available and falls back to a WebGL2 backend automatically — you write no detection code.

WHY IS IT BECOMING IMPORTANT? Because the numbers are unambiguous: four out of five lines of new Three.js work go to the new path. The old WebGLRenderer is maintained, not advanced. Features landing in r187 — LightMapper for baking indirect light, VXGIIrradiance for voxel global illumination, meshlet and visibility-buffer rendering pipelines, NodeMaterialInstance for materials sharing one shader — are WebGPU-only.

WHAT CAN IT DO? One measured result is striking: an independent 40-run benchmark on an RTX 5070 Ti found r187 cut WebGPU compileAsync() precompile time from a median 1,399.8 ms to 227.8 ms on a 48-tree scene — roughly 6× — because the scheduler now allows up to 16 shader pipelines compiling in flight instead of one. (Author's own caveat: a controlled desktop fixture, not a production-site result.)

WHY SHOULD I CARE? Shader compilation stalls are the #1 reason Awwwards-style 3D sites feel janky on first load. This attacks exactly that. And writing shaders in JavaScript removes the single biggest barrier between a MERN developer and real creative development — you no longer need GLSL to start.

WHAT CAN I BUILD WITH IT? Start embarrassingly small: a sphere whose vertices ripple and whose colour shifts over time, written entirely in TSL, no bundler — just an index.html with an import map and a main.js.

WHAT SHOULD I LEARN FIRST? Exactly five TSL nodes and nothing else: positionLocal, normalLocal, time, mix(), uniform(). Then positionNode and colorNode on MeshStandardNodeMaterial.

Upgrade gotchas if you have existing r186 code: PMREMs now use cube render targets and CubeUVReflectionMapping was removed, so materials will look slightly different; light registration changed from renderer.library.addLight(...) to CustomLight.registerNode(...); setViewport()/setScissor() no longer scale by pixel ratio when a render target is bound; TSL math now implicitly coerces operands to broader types. Also: Clock is deprecated — use Timer. The official advice when updating old projects is to move in increments of 10 releases, since deprecation warnings only last 10 releases.

RELEVANCE: 🟢 DIRECT   LEARNING PRIORITY: 🔥 HIGH   DEPTH: EXPERIMENT now, LEARN DEEPLY over the next few months.

🛡️ CYBERSECURITY

Today's security story is one story told three times, so let me treat it as one.

WHAT HAPPENED?

Three developer-infrastructure companies disclosed intrusions within days, all involving AI agents doing the attacking: WorkOS (internal sales app, 30 Oct, ARTEX framework named by its CEO), GitBook (infrastructure credentials, 2 Nov, "sophisticated, highly targeted attack using AI agents"), and reporting of a third involving probing between cloud providers. All three are confirmed by the companies' own bulletins.

WHAT IS THE VULNERABILITY?

There isn't one new vulnerability. That's the point. These were ordinary weaknesses — an exposed internal application, obtainable credentials, tokens that worked across more services than they should have. What changed is the speed and breadth of exploitation.

TERM: Credential blast radius.
Simple meaning: How much an attacker can reach using one stolen secret.
Real-world example: One leaked GitBook integration token also unlocks the Git repository it syncs with, which contains a .env with a database URL, which contains user emails. One secret, four systems.
Why it matters: Agents are exceptionally good at exactly this — taking one credential and systematically testing it everywhere it might work. A human does this in days; an agent does it in minutes.

HOW DOES THE ATTACK WORK? (defensive view only)

At a conceptual level: the agent is given a target and tools. It enumerates publicly reachable endpoints, reads error messages to infer the expected request shapes, identifies an internal application that is reachable from outside, extracts credentials or tokens, then immediately replays those credentials against every connected service it can discover. Each step is individually unsophisticated. The automation is what makes it dangerous. In the WorkOS case, investigators identified the attacker by distinctive user-agent strings (artex-enrich/1.0, norma/0.4) — a reminder that logging what you reject is as valuable as blocking it.

WHO IS AFFECTED?

Directly: GitBook and WorkOS customers. Broadly: anyone who stores secrets in a repo, reuses tokens across services, or has an internal admin tool reachable from the public internet.

WHY SHOULD A MERN DEVELOPER CARE?

Because your typical project shape is precisely the target profile: an Express API, a .env with a Mongo connection string and three third-party API keys, an admin route protected by a single check, and a deploy platform holding the whole lot. One year ago, a small misconfiguration here meant "someone might eventually find this". Today it means "an agent will find this on its next sweep".

HOW DO I PROTECT MY APPLICATION?

In order of value for effort:

  1. Audit your secrets today. git log --all -p | grep -i -E "api[_-]?key|secret|password|mongodb\+srv" on your own repos. Anything found is compromised and must be rotated — rewriting history does not un-leak it.
  2. Scope every token. One token per integration, minimum permissions, with an expiry. Never one "god token" that does everything.
  3. Validate JWTs fully. Signature, exp, iss — and aud. Reject tokens issued for another service. This is the week's single clearest lesson, courtesy of the MCP SDK CVEs.
  4. Never pass a user's token downstream. Exchange it for a new, narrower one, or use a vaulted service credential. Passthrough destroys your audit trail and turns your server into an exfiltration proxy for anyone holding that token.
  5. Rate limit and log rejections. Agent reconnaissance looks like an abnormal burst of 401s and 404s from one source. You cannot notice a pattern you don't record.
  6. No internal admin tool on the public internet without real auth. "Nobody knows the URL" is not access control.
  7. Treat agent config files as secrets. Commit ~/.claude/settings.json-style files to a private repo so unexpected changes show up in a diff.

WHAT SHOULD I LEARN?

JWT claim validation (deeply), OAuth 2.1 with PKCE and audience-bound tokens (what it is and why), and secret rotation as a routine habit rather than an emergency.

SAFE PRACTICAL LAB (fully local, nothing external)

Build two tiny Express servers on your own machine, api-a on port 3001 and api-b on port 3002, sharing one JWT signing secret.
Step 1: have both verify only the signature and expiry. Mint a token for api-a, then send it to api-b — watch it be accepted. That is the MCP SDK bug, reproduced in 20 lines.
Step 2: add aud: 'api-a' when signing, and in each server verify { audience: 'api-b' } with jsonwebtoken. Send the same token again — watch it be rejected.
Step 3: add a middleware that logs every rejected request with its IP and path, then hammer it with 50 bad requests and look at what reconnaissance actually looks like in your logs.
You will understand token audience binding permanently after this, and it takes under an hour.

🧠 WHAT I SHOULD LEARN TODAY

LEARN THIS #1 — Token audience binding (the aud claim)

WHAT IS IT? A token should declare which service it is for, and every service must reject tokens that name a different audience — even when the signature is perfectly valid.

WHY NOW? Because this exact omission just produced CVEs in the official MCP Python and TypeScript SDKs, and the patch ships with the check disabled by default. If the people who wrote the protocol missed it, you have missed it too.

WHY ME? You list Authentication and API security as goals, you issue JWTs in your own projects, and you intend to build agent backends where tokens will cross service boundaries constantly. This single check is the highest security-value-per-minute thing available to you.

WHAT EXACTLY SHOULD I LEARN? How to set aud when signing with jsonwebtoken; how to verify it with { audience: '...' }; what iss is and why you validate it too; and the rule "never forward a client's token to a downstream API — exchange it or use a service credential."

WHAT SHOULD I NOT WORRY ABOUT YET? The full OAuth 2.1 spec, PKCE implementation details, Client ID Metadata Documents, Enterprise-Managed Authorization. Those are for later. Today: one claim.

TIME: 1 hour

FREE RESOURCE: The MCP specification's authorization security considerations page, plus the jsonwebtoken npm README's audience option.

PRACTICAL MINI PROJECT: The two-Express-server lab in the Cybersecurity section above. Reproduce the vulnerability, then fix it. Watching the wrong token get accepted on your own machine is the part that makes it stick.

LEARN THIS #2 — Cache keys and tenant isolation

WHAT IS IT? Making sure every input that changes a cached result is part of that result's cache key — above all, who is asking.

WHY NOW? The highest-severity Next.js bug patched yesterday was exactly this failure, in a framework you use daily. You're reading the post-mortem of a mistake you are currently capable of making.

WHY ME? You're moving into backend and system design. Caching is the entry point to that whole field, and cache-key design is the part that actually separates people who've used Redis from people who can design with it.

WHAT EXACTLY SHOULD I LEARN? What belongs in a key; namespace prefixing per tenant; the cold-fill race and single-flight locking; Cache-Control: private vs public and the Vary header; cache tags for targeted invalidation.

WHAT SHOULD I NOT WORRY ABOUT YET? Distributed cache coherence, Redis Cluster, CDN purge APIs, multi-region replication. Single Redis, single app, correct keys. That's today.

TIME: 1 hour to understand, 1 hour to build

FREE RESOURCE: The Next.js November 2026 security advisories (read them as case studies) plus the Next.js Cache Components docs.

PRACTICAL MINI PROJECT: Two-tenant Express + Redis app. Build it wrong, watch tenant data cross over under concurrent load, then fix the key and prove it can't.

🔮 WHERE TECHNOLOGY IS GOING

TREND 1 — Prompts are becoming dependencies, and dependencies get attacked

WHAT THAT MEANS: Agent instructions, skills and tool configs are moving from hand-edited local files into manifests, lockfiles and automated update pipelines. Dependabot supporting APM is the formal start of this.
WHY IT MATTERS: Everything npm went through — typosquatting, malicious install scripts, dependency confusion, compromised maintainer accounts — is now available against agent context. The early warnings are already here: a malicious npm MCP package exfiltrating a wallet private key on every tool call, research showing malicious MCP servers passing five scanners clean, and tool poisoning measured at ~36.5% success across 20 model settings.
WHAT I SHOULD LEARN: Supply chain hygiene applied to AI: pin versions, review what you install, hash the complete tool definition (including input/output schemas and annotations, not just descriptions — a flipped destructiveHint changes approval behaviour with no visible text change), and never trust a tool description you didn't write.

TREND 2 — Your API's main caller is becoming a machine, not a human

WHAT THAT MEANS: OpenAI rebuilt Git's backend because agents push and fetch at machine scale — human engineers were never the load problem. Nearly a petabyte of Git traffic a day.
WHY IT MATTERS: Every assumption baked into normal API design — "a user clicks a few times a minute", "retries are rare", "a page of 20 results is plenty" — breaks when the caller is a loop. Rate limiting, idempotency, pagination, cost controls and timeouts all need rethinking.
WHAT I SHOULD LEARN: Idempotency keys, per-client quotas and token buckets, backpressure, cursor-based pagination, and designing responses that are cheap to consume in bulk.

TREND 3 — Attackers automated before defenders did

WHAT THAT MEANS: Three developer-infrastructure breaches in one week, all AI-agent-driven, all exploiting ordinary weaknesses at extraordinary speed. Reporting from Wiz, Google and CrowdStrike documents the same pattern more broadly; CrowdStrike spent ~$495M acquiring AI observability and AI red-teaming companies and shipped an "AI Kill Switch" to terminate runaway agents.
WHY IT MATTERS: The grace period between "misconfigured" and "breached" is gone. Security work that was reasonable to defer is no longer reasonable to defer.
WHAT I SHOULD LEARN: Least privilege by default, short-lived scoped credentials, routine secret rotation, and logging rejections so reconnaissance is visible.

TREND 4 — The browser GPU is becoming a real compute platform

WHAT THAT MEANS: Three.js is spending ~80% of its core development on WebGPU and TSL. WebGPU has been available across major browsers for about a year. Shader authoring is moving into JavaScript.
WHY IT MATTERS: The barrier to creative development is collapsing. You no longer need GLSL to write shaders, and you can now run general-purpose parallel computation in a browser tab.
WHAT I SHOULD LEARN: TSL node basics now; WebGPU compute shaders later. Being early here is a genuine differentiator — most JS developers still think "shaders = GLSL = not for me".

TREND 5 — AI is moving into the tools people already use, not into new chat windows

WHAT THAT MEANS: Agents are being embedded in existing professional software rather than shipped as separate apps: Google's cheminformatics Skills inside Antigravity, Codex used for CAD and PCB work, Kimi's agents editing Unity/Unreal/Blender projects directly, Siri gaining the ability to act inside third-party apps in iOS 27.3. Domain knowledge is layered on through Skills or configs rather than new tools.
WHY IT MATTERS: The integration surface — how an agent safely reaches into an existing app with the right identity and permissions — is becoming the real product. AWS publishing guidance on on-behalf-of token exchange so an agent calls an API as the user rather than as a service account is exactly this.
WHAT I SHOULD LEARN: Tool/function calling, MCP, and on-behalf-of authorization. This is the backend layer underneath every one of those features — and it is where your existing skills are worth the most.
