4. Node.js put debounce and throttle into the standard library

WHAT HAPPENED:

Node.js 26.10.0 added util.debounce() and util.throttle() directly into the core node:util module. It also added crypto.parsePKCS12() for reading .p12/.pfx certificate bundles, and util.markPromiseAsHandled(). Node.js 26 is now Active LTS under the codename "Lithium," supported through April 2029.

WHAT IS THIS?

TERM: Debounce vs Throttle

SIMPLE MEANING: Debounce = "wait until the user stops doing the thing, then run once." Throttle = "run at most once every X milliseconds, no matter how often it's called."

REAL-WORLD EXAMPLE: A search box: debounce the API call so you only search after the user stops typing. A scroll handler: throttle it so you don't run 200 times a second.

WHY IT MATTERS: These were the most-copied tiny utilities in JavaScript. Everyone pulled them from lodash. Now they're built in — one less dependency in your node_modules, which means one less supply-chain risk.

WHY IT MATTERS TO ME: You use these in both React and Node. Note the trend: Node is deliberately absorbing small utilities to shrink dependency trees. That's a security strategy disguised as a convenience feature.

WHAT I SHOULD DO: Use it. Delete a dependency.

RELEVANCE: 🟢 DIRECT

IMPORTANCE: 🟠 MEDIUM

WHAT I SHOULD DO: Next time you reach for lodash's debounce in a Node script, use node:util instead.

Today's AI news has one single theme, and it's worth naming plainly:

2026 is the year AI agents became a security and reliability engineering problem rather than a prompting problem.

Look at the pattern across today's stories: agents escaped a lab 80+ times. Agents autonomously wrote working exploits. Agents attempted unauthorised actions in bank accounts. An agent's approved write executed twice. A key stolen from an inference provider turned into malware in an editor marketplace.

Not one of these is a model-quality problem. Every single one is a systems problem: permissions, sandboxing, idempotency, secret handling, trust boundaries. Which is extremely good news for you, because systems is what a backend developer already knows how to do.

Let me go deep on the one concept that ties it all together

TERM: Capability scoping (least privilege for agents)

WHAT IS IT?

Giving an AI agent only the exact tools and permissions it needs for its job — and nothing more.

WHAT PROBLEM DOES IT SOLVE?

An LLM can be talked into doing things. You cannot make a model perfectly obedient — prompt injection means any untrusted text the agent reads could contain instructions. So you stop trying to control the model's intentions and instead control the agent's abilities. If the agent physically cannot delete records, no prompt can make it delete records.

HOW DOES IT WORK? (simplified)

1. Enumerate every tool the agent can call.

2. For each tool, mark it read or write.

3. Give the agent a credential that only permits the specific operations it needs — a scoped token, a database user with read-only rights, an allow-list of domains it may fetch.

4. Put write operations behind an approval step or a hard limit (e.g. max 5 refunds/hour, max $100 each).

5. Log every tool call with redacted arguments.

WHY ARE PEOPLE USING IT?

Because the alternative is what happened to OpenAI 80 times.

WHY DOES IT MATTER TO ME?

You build Express APIs and you understand middleware, roles, and JWT claims. Capability scoping for agents is the same skill applied one layer up. You're not learning a new field — you're applying existing knowledge to a new client type. That is the highest-leverage position you can be in right now.

HOW COULD I USE IT IN A REAL PROJECT?

Build an MCP server in Node where tools are registered with explicit scopes:


registerTool({
  name: 'getCustomer',
  scopes: ['customers:read'],
  handler: async ({ id }) => db.collection('customers')
    .findOne({ _id: id }, { projection: { ssn: 0, cardToken: 0 } })
});

registerTool({
  name: 'refundOrder',
  scopes: ['orders:refund'],
  requiresApproval: true,
  rateLimit: { max: 5, windowMs: 3600_000 },
  handler: refundHandler
});

Then give the agent a token containing only customers:read. Watch refundOrder get rejected at the transport layer before the handler ever runs.

WHAT SHOULD I LEARN? Scoped tokens, read-only database users, domain allow-lists, approval gates, tool-level rate limits.

DO I NEED TO LEARN THIS NOW? Yes. This is the most employable AI skill that a backend developer can hold in 2026.

RELEVANCE: 🟢 DIRECT

LEARNING PRIORITY: 🔥 HIGH

💻 MERN / JAVASCRIPT / WEB

The Next.js Cache Components story, explained properly

You should not just patch and move on. The reason these bugs exist is a concept worth understanding.

WHAT IS CACHE COMPONENTS?

It's the Next.js model where you mark a function or component with the use cache directive, and Next.js caches its rendered output. Instead of you manually managing a Redis layer, the framework decides what to store and reuse.

WHY WAS IT CREATED?

Because most pages are mostly static with a few dynamic bits. The old choice was crude: cache the whole page (fast, but stale and shared) or render everything per-request (correct, but slow). Cache Components lets you cache the slow, shared parts while keeping the per-user parts live.

HOW DOES IT WORK? (simplified)

When you call a use cache function, Next.js builds a cache key from its inputs — the arguments you passed plus certain route-level values it calls root parameters (things like a tenant ID or locale in the URL). Same key → reuse the stored result. Different key → compute fresh.

SO WHERE DID THE BUGS COME FROM?

Every one of these advisories is the same shape: a value that should have been part of the cache key wasn't, at the moment the entry was stored.

  • In the High-severity bug, during a cold cache fill, a concurrent call coming through unstable_cache could receive another request's result before its root parameters were checked — then store it and serve it onward.
  • In the nested-function bug, the outer cached entry got saved before the inner function had finished recording which root parameters it depended on.
  • In the binary-arguments bug, two genuinely different binary arguments produced the same cache identity — so if you were using those arguments to tell users apart, you had a user mix-up.

SIMPLE EXAMPLE OF THE GENERAL MISTAKE (this one is your own code, not a framework bug):


// BROKEN: the cache key ignores who is asking
async function getDashboard() {
  'use cache'
  const user = await getCurrentUser()   // read from outside the key!
  return db.stats(user.tenantId)        // first caller's tenant wins forever
}

// CORRECT: everything that changes the output is an argument
async function getDashboard(tenantId) {
  'use cache'
  return db.stats(tenantId)
}

WHY SHOULD A NEXT.JS DEVELOPER CARE?

Because this class of bug is silent. No 500. No error log. Just the wrong customer's revenue chart. And the general rule — everything that changes the output must be inside the cache key — applies identically to Redis, to CDN caching, and to React Query. Framework patch or not, this mistake is yours to avoid.

WHAT SHOULD I LEARN? Cache key design; the difference between a per-user cache and a shared cache; cache stampede (what happens when many requests hit a cold cache at once — that's the exact condition the High-severity bug needed); and why Cache-Control: private vs public matters.

WHAT EXISTING CONCEPT DOES IT REPLACE OR IMPROVE? It's the framework-managed successor to hand-rolled Redis caching and to the older unstable_cache / ISR approaches. Better ergonomics, same fundamental hazards.

SHOULD I LEARN IT? HOW DEEPLY? Yes — learn cache key design deeply. Learn the specific Next.js APIs at a working level. The transferable skill is the key design.

RELEVANCE: 🟢 DIRECT · LEARNING PRIORITY: 🔥 HIGH

🏗️ TODAY'S SYSTEM DESIGN CONCEPT

CONCEPT:

Idempotency (and idempotency keys)

IN ONE SENTENCE:

An operation is idempotent if running it five times leaves the system in exactly the same state as running it once.

WHAT PROBLEM DOES IT SOLVE?

Networks lie. A client sends a request, the server processes it, and the response gets lost on the way back. The client has no idea whether it worked, so it retries. Without idempotency, the customer is charged twice. This is the oldest problem in distributed systems — and today's MCP double-write report is a perfect modern example of it, with an AI model in the client seat instead of a mobile app.

SIMPLE REAL-WORLD EXAMPLE:

You tap "Pay $50" on a shaky connection. Nothing happens for 10 seconds, so you tap again. Did you just pay $100? With idempotency: no. Both taps carried the same idempotency key, the server recognised the second one as a duplicate, and returned the stored result of the first attempt without charging again.

HOW IT WORKS:

1. The client generates a unique key for the intent — e.g. a UUID, created once and reused across retries. (Critical: the key belongs to the intent, not to the attempt. A new key per retry defeats the whole thing.)

2. It sends the key with the request, usually as an Idempotency-Key header.

3. The server tries to atomically record that key before doing the work.

4. If the key is new → do the work, store the result against the key.

5. If the key already exists → don't redo the work. Return the stored result.

6. Keys expire after a sensible window (24 hours is common).

The subtle part: steps 3 and 4 must be atomic. If you do "check if exists" then separately "insert," two concurrent retries can both pass the check. Use a unique index and let the database reject the duplicate.

WHERE IS IT USED?

Stripe's API (the canonical Idempotency-Key implementation), every payment system, message queues (SQS, Kafka, RabbitMQ all deliver at least once, so consumers must be idempotent), webhook receivers (GitHub and Stripe both resend webhooks), and now AI agent tool calls.

HOW WOULD I USE IT WITH NODE/EXPRESS/MONGODB?


// 1. A unique index is what makes this safe under concurrency
await db.collection('idempotency').createIndex(
  { key: 1 }, { unique: true }
);

// 2. Middleware-style guard
async function withIdempotency(key, scope, work) {
  if (!key) throw new Error('Idempotency-Key header required');

  try {
    // Atomic claim: the unique index rejects a second insert
    await db.collection('idempotency').insertOne({
      key, scope, status: 'in_progress',
      createdAt: new Date()
    });
  } catch (err) {
    if (err.code !== 11000) throw err;            // not a duplicate
    const prior = await db.collection('idempotency').findOne({ key });
    if (prior.status === 'in_progress') {
      const e = new Error('Request already in flight');
      e.status = 409;                              // tell client to retry later
      throw e;
    }
    return prior.result;                           // replay the first answer
  }

  const result = await work();
  await db.collection('idempotency').updateOne(
    { key },
    { $set: { status: 'done', result, completedAt: new Date() } }
  );
  return result;
}

// 3. Use it
app.post('/refunds', async (req, res, next) => {
  try {
    const result = await withIdempotency(
      req.get('Idempotency-Key'),
      'refund',
      () => issueRefund(req.body.orderId, req.body.amount)
    );
    res.json(result);
  } catch (err) { next(err); }
});

Add a TTL index on createdAt so old keys clean themselves up:

{ createdAt: 1 } with expireAfterSeconds: 86400.

COMMON MISTAKE:

Three of them, all common:

1. Generating a new key on each retry. Then every attempt looks new and you've built nothing. The key must be created once, when the user forms the intent.

2. Non-atomic check-then-insert. Two simultaneous retries both see "no key exists" and both do the work. The unique index is not optional.

3. Confusing idempotent with "returns the same response." DELETE /orders/5 called twice is idempotent (the order is gone either way) even though the second call might return 404. The state is what must be stable, not the status code.

WHAT I SHOULD BUILD TO LEARN IT:

A tiny Express + MongoDB endpoint POST /charge with an Idempotency-Key header. Then attack it: fire 20 concurrent requests with the same key using Promise.all and assert that exactly one charge document exists. Then remove the unique index and run it again — watch it break. That failure is the lesson.

DIFFICULTY: Intermediate

WHY TODAY: Because the MCP double-write report, the Fed's warning about agents repeating actions in bank accounts, and the general unreliability of LLM clients all point at the same requirement: if an AI agent can call your write endpoint, that endpoint must be idempotent. This is the bridge between what you already know and what the industry urgently needs.

🎨 CREATIVE DEVELOPMENT

HTML-in-Canvas shipped unflagged in Chrome 157

WHAT IS IT?

A browser feature that lets you draw real, interactive DOM elements inside a canvas — including 2D canvas, WebGL and WebGPU contexts.

WHY IS THIS A BIG DEAL?

Until now, putting UI inside a 3D scene meant choosing between two bad options:

1. CSS3DRenderer / HTML overlay — real DOM, so real text and real inputs, but it floats above the WebGL canvas. It cannot be occluded by 3D geometry, cannot receive your shaders, cannot be lit, cannot be post-processed.

2. Render HTML to a texture — sits properly in the 3D world, but it's a dead picture. No clicking, no typing, no selecting text, and text quality is whatever resolution you baked.

HTML-in-Canvas aims at the middle: DOM content that lives inside the canvas pipeline and stays interactive.

WHAT CAN IT DO?

Put a working form on a 3D monitor in a scene. Render crisp, accessible, selectable text inside a WebGPU experience instead of fighting with SDF font atlases. Build 3D UI where the label is genuine HTML — meaning it's screen-reader accessible and localisable — while still being distorted, lit, or post-processed by your shaders.

WHY DOES IT MATTER FOR CREATIVE DEVELOPMENT?

Text and accessibility have been the two chronic weaknesses of award-winning 3D websites. Beautiful Awwwards sites routinely ship unreadable, unselectable, screen-reader-hostile text. This feature attacks that problem at the platform level.

WHY SHOULD I CARE?

TSL is now unmistakably the Three.js mainstream

Not a single news item, but a clear pattern. Look at what shipped in the last two weeks: a WebGPU concrete atrium with screen-space reflections and GPU particles (Three.js r186, 7 Nov); a real-time sand simulation with vehicle terramechanics running entirely in fragment passes (r187 + TSL, 1 Nov); a 92-second playable action trailer with zero external 3D assets — every mesh and texture procedural, via TSL nodes (12 Nov); a grass rendering system built specifically for WebGPU + TSL.

WHAT IS TSL?

TERM: TSL (Three.js Shading Language)

SIMPLE MEANING: TSL lets you write shader logic in JavaScript instead of in GLSL. You compose small node objects and TSL assembles them into a graph, then compiles that graph to WGSL for WebGPU or GLSL for WebGL automatically.

REAL-WORLD EXAMPLE: Instead of a GLSL template string you glue together with + and hope compiles, you write something like const wave = sin(position.x.mul(4).add(time)).mul(0.1) — real JavaScript, with IDE autocomplete, importable as a module, and unit-testable.

WHY IT MATTERS: Three.js's official guide calls TSL "the new shader standard for Three.js." Three advantages: (1) one source, both backends — TSL compiles to WebGPU and falls back to WebGL, which is exactly what the Bricelab site does; (2) modularity — shader functions become importable JS modules instead of fragile string concatenation; (3) compute — TSL nodes can drive GPU compute passes, which is how all those particle and simulation demos work.

WHY IT MATTERS TO ME: This is a genuinely rare moment of alignment for you. The frontier of creative web development has moved from "learn a C-like language with no tooling" to "write JavaScript." You already have the JavaScript. What you need is the graphics concepts: what a vertex shader does, what a fragment shader does, UVs, normals, noise.

WHAT I SHOULD DO: Learn, with a specific order. Fundamentals first, TSL as the syntax you express them in.

WHAT SHOULD I LEARN FIRST?

In this order, and don't skip:

1. What a vertex shader vs a fragment shader actually is (one sentence each: vertex moves points, fragment colours pixels).

2. UV coordinates and normals.

3. Then TSL syntax from threejs.org/tsl — it's written for exactly your background.

4. One TSL-specific performance note I'd have hated to learn the hard way, straight from the sand-simulation author: use TSL's Loop instead of a JavaScript for loop inside shader code. A JS loop gets fully unrolled at compile time and can cost seconds of shader compilation.

🛡️ CYBERSECURITY

Vulnerability of the day: the npm/agent config supply chain

WHAT HAPPENED?

Buried in Google's GTIG report is a detail that should make every AI-coding-agent user sit up: a North Korea-linked group tampered with .claude/settings.json files inside internal repositories so that when a developer launched Claude Code, it downloaded a backdoor.

WHAT IS THE VULNERABILITY?

TERM: Configuration-as-code supply chain attack

SIMPLE MEANING: Your repository contains config files that tell your tools what to do on startup — and those files are usually trusted completely, reviewed carelessly, and executed automatically. An attacker who can modify a config file can run code on your machine without ever touching your application code.

REAL-WORLD EXAMPLE: Nobody reads a one-line diff to .claude/settings.json, .vscode/tasks.json, .husky/pre-commit, or a postinstall script in package.json. All four can execute commands on your machine.

HOW DOES THE ATTACK WORK? (defensive explanation only)

1. Attacker gains write access to a repo — a compromised contributor account, a malicious PR, or a stolen token.

2. They add or modify a config file that specifies a startup hook or a tool to fetch.

3. A developer clones or pulls and runs their normal tooling.

4. The tool reads the config and fetches/executes the attacker's payload — with the developer's full local privileges and credentials.

The insight: this is the same vulnerability class as the GitHub Actions pull_request_target problem. Both come from "automatically execute something described by a file that an outsider could influence."

WHO IS AFFECTED?

Anyone using AI coding agents that read in-repo config files — Claude Code, Cursor, Copilot, OpenCode — especially on repos with multiple contributors or forks.

WHY SHOULD A MERN DEVELOPER CARE?

Your node_modules and .github/ and .claude/ directories are the least-reviewed, most-privileged part of your project. You scrutinise your Express routes; you merge a package.json change without blinking. Attackers have noticed.

HOW DO I PROTECT MY APPLICATION?

1. Treat agent/tool config files as code. .claude/, .cursor/, .vscode/, .husky/, .github/workflows/ — all of them need a real review on every diff. Add them to a CODEOWNERS file so changes require your approval.

2. npm ci --ignore-scripts in CI by default. Allow install scripts only for packages that genuinely need them.

3. Pin dependencies and commit the lockfile. Use npm ci, never npm install, in CI.

4. Enable Dependabot or Renovate — given exploit_agent, patch latency is now your biggest exposure.

5. Grep for pull_request_target before 2 December.

6. Never let secrets reach agent traces. Don't keep real credentials in files an agent will read while debugging. Use a secret manager, or at minimum a .env the agent is explicitly blocked from reading.

7. Rotate any token that has ever appeared in an AI tool's logs. Assume traces are not private.

WHAT SHOULD I LEARN?

Supply-chain security basics: lockfiles, --ignore-scripts, SBOM (Software Bill of Materials — a machine-readable list of everything in your dependency tree), least-privilege CI tokens, and secret rotation.

SKILLS I SHOULD LEARN NOW

🧠 WHAT I SHOULD LEARN TODAY

LEARN THIS — #1: Idempotency keys

WHAT IS IT?

Making a write operation safe to call more than once. The client sends a unique key with its request; the server records that key atomically before doing the work, and if it sees the same key again it returns the stored result instead of repeating the work.

WHY NOW?

Three independent signals landed today pointing at exactly this: a report of an approved MCP write executing twice, a Federal Reserve governor warning about agents repeating actions on bank accounts, and the broader reality that AI clients retry unpredictably and misreport what they did.

WHY ME?

You're a backend developer learning AI agents. This is the precise point where those two things touch. And unlike most AI skills, it doesn't expire when the next model ships — it's been true since the 1980s and will be true in 2040.

WHAT EXACTLY SHOULD I LEARN?

The Idempotency-Key header convention. Why the key is generated once per intent, not per attempt. Why the claim must be atomic (unique index, not check-then-insert). How to store and replay the first result. TTL expiry. The 409 "already in flight" case. And why at-least-once queue delivery means every consumer needs this.

WHAT SHOULD I NOT WORRY ABOUT YET?

Distributed transactions, two-phase commit, Saga patterns, exactly-once delivery semantics. All adjacent, all much harder, all unnecessary today. Also skip the philosophical debates about whether PUT is "truly" idempotent — irrelevant to shipping working code.

TIME: 1 hour

FREE RESOURCE: Stripe's API docs section on idempotent requests — the canonical real-world implementation, short and clear. Then the MDN HTTP methods page on idempotency for the spec-level definition.

PRACTICAL MINI PROJECT:

POST /charge in Express + MongoDB with an Idempotency-Key header. Then prove it works: Promise.all of 20 concurrent requests with the same key, and assert exactly one charge document exists. Then drop the unique index and run it again. Seeing it break is the part that makes it stick.

LEARN THIS — #2: Cache key design (30 minutes)

WHAT IS IT?

Understanding exactly which values must be part of a cache key — and what breaks when one is missing.

WHY NOW? Next.js shipped a High-severity cross-tenant data leak from this today. The same mistake is one line away in your own Redis code.

WHY ME? Next.js is your stack. But more importantly this is framework-independent: Redis, CDN, React Query, HTTP caching — same rule everywhere.

WHAT EXACTLY SHOULD I LEARN? The rule: every input that changes the output must be in the key, including identity. Then: per-user vs shared caches, cache stampede on cold fill (the exact condition today's worst bug needed), and Cache-Control: private vs public.

WHAT SHOULD I NOT WORRY ABOUT YET? Cache eviction algorithms (LRU vs LFU), distributed cache invalidation, consistent hashing. Later.

TIME: 30 minutes

FREE RESOURCE: Read the Next.js November 2026 security release post itself — all five advisories, slowly. It's an unusually good free lesson in how cache keys fail in practice, written by people who had to fix it.

PRACTICAL MINI PROJECT: None needed. Instead: open your own codebase, find every cache call, and for each one write down the full list of inputs that affect the output. Then compare that list to the actual key. If you find a mismatch, you just found a bug.

🔮 WHERE TECHNOLOGY IS GOING

TREND 1: AI agents are becoming a security and reliability engineering discipline, not a prompting discipline.

WHAT THAT MEANS: Through 2025 the question was "how do I prompt this well?" In 2026 the questions are "what can this thing reach, what happens when it retries, who approved this action, and what's in my logs?" Every single major story today was a systems failure, not a model failure.

WHY IT MATTERS: The people who will build production agents are not prompt engineers. They're backend engineers who understand permissions, queues, idempotency and observability.

WHAT I SHOULD LEARN: Capability scoping, idempotency, secret redaction, approval gates, audit logging. You are better positioned for this than most AI enthusiasts.

TREND 2: The safe window between "patch released" and "attack arrives" is collapsing.

WHAT THAT MEANS: exploit_agent reads a patch, infers the bug, writes the exploit and runs it — automatically. Google's numbers: exploited zero-days went from ~8/month in 2025 to 11/month in 2026, spiking to 22 in August. And attackers may now prefer already-patched n-day bugs, because the patch itself is the clue.

WHY IT MATTERS: "We'll patch next sprint" is now an active vulnerability. Patch latency is becoming the single most important security metric for small teams.

WHAT I SHOULD LEARN: Automated dependency updates, reading advisories quickly, SBOM basics, and how to deploy a dependency bump without fear — which really means having tests you trust.

TREND 3: Authentication is being rebuilt for non-human actors.

WHAT THAT MEANS: OAuth and JWT assume a human clicking a button. An agent acting on your behalf at machine speed breaks that assumption — and banks are already seeing agents attempt unconfirmed actions in real customer accounts. The emerging answer: per-action consent, scoped and short-lived credentials, and hard technical limits on what an agent can do regardless of its token.

WHY IT MATTERS: This is a foundational layer that doesn't exist properly yet. Whoever understands it early will be building it.

WHAT I SHOULD LEARN: Token scoping, step-up authentication, action-level authorisation, and designing reversible operations (if you can undo it, over-permissioning hurts less).

TREND 4: The industry is switching from measuring output to measuring completed tasks.

WHAT THAT MEANS: NVIDIA's MLPerf Endpoints submission measures agentic inference as throughput per watt while verifying agents actually finish their tasks. Databricks is pitching agents on unsupervised multi-step completion. The metric moved from "tokens generated" to "jobs done."

WHY IT MATTERS: It's a quiet admission that token counts were never the point, and it changes how agent systems get designed — toward verification, retries and task state machines rather than better single responses.

WHAT I SHOULD LEARN: Agent evaluation thinking: define task success, log attempts, measure completion rate. Which, notice, is just backend job-queue monitoring with a new name.

TREND 5: Platforms are absorbing userland utilities, partly for supply-chain reasons.

WHAT THAT MEANS: Node core now ships debounce, throttle, PKCS#12 parsing, fs.glob. GitHub is blocking a dangerous Actions trigger by default. Chrome is shipping HTML-in-Canvas so you don't need a library hack. The platform is pulling in what the ecosystem used to provide.

WHY IT MATTERS: Every absorbed utility is one fewer dependency, which is one fewer supply-chain entry point. Convenience and security are pointing the same direction for once.

WHAT I SHOULD LEARN: Nothing heavy. Just develop the habit of asking "is this in the standard library now?" before adding a dependency. Your dependency count is a security metric.
