🤖 THE MAIN EVENT — SYSTEM ONE MODELS

This is the thing to understand today. It reframes everything I told you this morning.

TERM: System One / System Two model

SIMPLE MEANING: The names come from Daniel Kahneman's book Thinking, Fast and Slow. System One thinking is fast, automatic and intuitive — you see a face and instantly know it's angry. System Two is slow and deliberate — you multiply 47 × 83 step by step.

Applied to models: an LLM is a System Two model. It reasons, it generates tokens one at a time, it takes seconds. A System One model is fast and precise, answers in a single forward pass, generates no tokens at all, and is purpose-built for one shape of question.

REAL-WORLD EXAMPLE: "What is this invoice total?" An LLM reads the document, reasons about it, and generates the characters 1, ,, 2, 4, 7, ., 5, 0 one at a time — several seconds, output tokens billed. A System One extraction model returns the number 1247.50 in one pass, with a confidence score and the character offsets where it found it, in under a second, and bills you for input only.

WHY IT MATTERS: Most production AI calls are not creative writing. They are: extract this field, classify this input, pick the next action, score this risk. Using a token-generating reasoning model for those is like using a freight train to deliver a letter.

The three model families now in play

ModelClassAnswers withWho
JevSystem One decisionProbabilities across a fixed list of options you supplyTypeSafe
ClefSystem One decisionPicks among options, returns a probability for eachTypeSafe
ClairicSystem One extraction (new)Actual values: numbers, dates, names, lists, forecastsCloudflare
LLMsSystem TwoOpen-ended textEveryone

Cloudflare's framing is clean. Model tasks want one of three output shapes:

  1. A number or typed value → Clairic (extraction model)
  2. A choice from a fixed set → Clef / Jev (decision model)
  3. Open-ended text → an LLM

Only the third genuinely needs an LLM. The industry has spent two years using LLMs for all three.

What makes Clairic different from the decision models

Decision models need you to list the possible answers in advance so they can assign probabilities. But Cloudflare noticed a huge category of calls where you can't list the answers:

What's the invoice total? When was this delivered? How many days late is it? What will this repair cost? What will traffic look like over the next 24 hours?

You cannot enumerate every possible invoice total. So Clairic returns three kinds of output:

  • Extracted values — text copied straight from the input (a name, an order ID). Comes back as a span with character offsets and a confidence score.
  • Computed values — numbers, dates, times, durations, lists either read from the input or worked out from it, following their type's rules (e.g. two decimal places for currency), with confidence scores.
  • Estimated values — things the input doesn't state but gives evidence for, returned as a distribution. Numbers come with an 80% range rather than one fake-precise figure.

Note the character offsets. That's the detail that matters for real applications. An LLM tells you the total is $1,247.50 and you have to trust it. Clairic tells you the total is $1,247.50 and points at characters 4,120–4,128 where it found it. You can highlight it in the UI. You can verify it. You can audit it. Hallucination becomes checkable instead of invisible.

WHY DOES THIS MATTER TO ME?

Directly, in three ways:

1. It changes what you build. Every "upload a document and we'll pull the data out" feature — invoices, receipts, CVs, forms — is currently built badly with an LLM and a prayer that the JSON parses. With an extraction model you get typed values, confidence scores and source offsets. That's a product you can actually ship to a paying customer.

2. It's cheaper in a way that changes architecture. Input-only billing, sub-second latency. Things you currently can't afford to do per-request become free to do per-request.

3. Your MongoDB experience becomes relevant in a new way. Confidence scores mean your schema changes. You stop storing { total: 1247.50 } and start storing:

// A document AFTER extraction-model thinking
{
  invoiceTotal: {
    value: 1247.50,
    confidence: 0.94,
    span: { start: 4120, end: 4128 },   // where in the source
    source: 'extracted'                  // vs 'computed' vs 'estimated'
  },
  deliveryDate: {
    value: '2026-10-14',
    confidence: 0.71,
    source: 'computed'
  },
  repairCost: {
    estimate: 840.00,
    range80: [610.00, 1180.00],          // honest uncertainty
    source: 'estimated'
  },
  _needsReview: true   // because deliveryDate confidence < 0.8
}

That _needsReview flag is the whole game. It's how you build an AI feature that degrades gracefully instead of silently lying. Low confidence routes to a human; high confidence auto-processes. Box described exactly this pattern in the Decisions API announcement I quoted this morning — lower-confidence cases go to reviewers — but I didn't explain why they could do that. This is why: confidence is a first-class output.

💸 COST ENGINEERING — CLOUDFLARE'S 68% CUT

Real numbers from a real production system. This is the free lesson most people will skip.

How the cost doubled without anyone changing the architecture

March 2026$1.22

After optimisation$0.77

Three causes, and the second one is the interesting one:

Cause 1 — Better models made humans write bigger diffs. Their most expensive "full review" tier went from 59% of reviews in March to 65% in August. Cloudflare's own explanation: models got more capable, so engineers produced bigger and more complex changes, so more work landed in the expensive tier. The AI getting better made the AI bill go up, through human behaviour, not through pricing. Nobody forecasts that.

Cause 2 — A deliberate quality decision cost them 47%. In early August they moved every reviewer onto Anthropic models because their evals showed better performance on this specific workload. Cost per job went $1.38 → $2.03 immediately. Their internal standards reviewer went from ~$0.25 to $0.88 per review — more expensive than the coordinator agent itself. That was a defensible choice made with eval data, and it still nearly doubled the bill.

Cause 3 — and this is the one that should change how you think:

Cache hit rate improved from 85.7% (April) → 97% (September). Meanwhile tokens per review more than tripled, from 0.91 million to 2.99 million.

Read that twice. Their caching got dramatically better and their bill went up. A 97% hit rate on three times the tokens still costs far more than 85.7% on a third of the tokens, even at cheap cache-read rates.

THE LESSON: This morning I gave you a caching exercise and framed hit rate as the goal. That was incomplete advice. A cache hit rate is a ratio, and optimising a ratio tells you nothing about the absolute bill. You can be winning on every dashboard and losing on the invoice. Always track the absolute total alongside the rate.

Where the savings came from

About 40% from their own code, 60% from model selection and effort levels. And the result was not a quality-for-cost trade: median review time improved from 4m 09s to 1m 32s while cost fell 68%. The bloat was waste, not quality.

One more verified detail worth noting: they migrated the reviewer to OpenCode v2 (a ground-up rewrite). Before switching they ran every review in every canary repo on both v1 and v2 in comparative shadow mode, found the two agreed on the approval decision in 98% of merge requests, then cut over in one go.

TERM: Shadow mode / shadow deployment

SIMPLE MEANING: Run the new system alongside the old one on real production traffic, but only act on the old system's output. Compare the two. When they agree often enough, switch.

WHY IT MATTERS TO ME: This is how you ship a risky change to an AI system without a staging environment that can possibly simulate reality. You already know how to duplicate a request in Express middleware — that's all this is. And "98% agreement" is a far better release criterion than "it worked when I tried it."

WHAT I SHOULD LEARN: Shadow deployment, and cost-per-request as a tracked metric next to latency and error rate.

🛡️ SECURITY — THE THREE STORIES THAT AREN'T ABOUT YOUR STACK

1. The agentic intrusion — and the delimiters that gave it away

WHAT HAPPENED: Unit 42 observed, within two hours of initial compromise of a European government entity: password hashes and 2FA secrets accessed; anonymous LDAP queries via curl against the domain controller hunting for the administrator account; host reconnaissance for DNS/AD integration, internal hosts, privileged groups and interactive users; an NTLM-relay tunnel into Active Directory; and an attempted Domain Admin escalation.

THE TELL: "Each command batch is wrapped in section-header delimiters, such as ==SHELLUSER== and ==PASSWD==. These delimiters produce machine-parseable output for an AI model to read."

TERM: NTLM relay

SIMPLE MEANING: NTLM is an old Windows authentication protocol. In a relay attack you don't crack a password — you catch an authentication attempt in transit and forward it to a different service, which accepts it as if you were the original user. Authentication without ever knowing the secret.

WHY SHOULD A DEVELOPER CARE? Two reasons, and neither is about PHP:

(a) The attacker's engineering is your engineering. Why delimiters? Because an agent has to parse its own tool output, and raw shell output is unreliable to parse. So you wrap it in markers you can regex. You have written this exact code. If you've built anything agentic, you've made the same decision for the same reason. That should land uncomfortably — the offensive and defensive sides of agent engineering are the same skills.

(b) Two hours, and the time is going to shrink. Hash and MFA-secret harvesting to attempted Domain Admin in under two hours. That compresses because the work is automated. Every patch window you've mentally budgeted as "I'll get to it this week" is being priced against this clock.

HOW DO I PROTECT MY APPLICATION? Honestly: the AD/NTLM parts aren't yours to defend. What is yours:

  • Assume compromise is fast. Short-lived credentials beat strong ones, because a stolen 15-minute token is near-worthless.
  • Don't store MFA secrets recoverably. The first thing the agent went for was the auth database.
  • Log and alert on shape, not just volume — rapid sequential enumeration looks different from human browsing even at low request rates.

SAFE PRACTICAL LAB: Nothing offensive. Instead: take an agent you've built, and write down every tool it can call and the blast radius of each if the agent were fully hostile. Most people discover one tool that's far too powerful. That inventory is the exercise.

RELEVANCE: 🟢 DIRECT (as an agent builder)  |  LEARNING PRIORITY: 🔥 HIGH

2. Low-and-slow scanning — the attack on your rate limiter

WHAT HAPPENED: 21 compromised nodes, 216 filtered targets across 12+ countries and sectors including government, finance, logistics, airports and payments. The method, per CYFIRMA: deliberately low-volume, paced, with nodes rotated and abandoned at the first sign of blocking or rate-limiting — specifically so that threshold-based alerting won't fire.

WHY SHOULD A MERN DEVELOPER CARE? Because this is a direct attack on a category of code you write constantly. Your express-rate-limit config — 100 requests per 15 minutes per IP — is a threshold. This technique is the documented playbook for staying under it. And "rotate the node the moment it gets blocked" means the attacker treats your 429 response as feedback: your rate limiter is telling them exactly where the line is.

HOW DO I PROTECT MY APPLICATION?

  • Don't make your limits informative. Returning a precise Retry-After and a clean 429 is good UX for honest clients and free reconnaissance for scanners. Consider degrading (slow responses, generic errors) rather than cleanly announcing the boundary.
  • Rate-limit on behaviour, not just count. 30 requests that each probe a different nonexistent admin path is not the same as 30 requests to your API, even though a counter sees one number.
  • Alert on cumulative low-volume patterns. One request per minute per IP from 21 IPs, all hitting 404s on sensitive paths, is invisible per-IP and obvious in aggregate.
  • Log 404s on sensitive paths as a security signal, not noise to be filtered out.

WHAT SHOULD I LEARN? The gap between rate limiting (protecting capacity) and abuse detection (protecting against intent). They're different problems and most codebases only implement the first.

SAFE PRACTICAL LAB: On your own app: write a script that hits one endpoint once every 20 seconds from a single IP for ten minutes, requesting paths like /admin, /.env, /wp-login.php. Then check whether anything in your logging or monitoring would have told you. For most projects, the honest answer is no. That's the finding.

RELEVANCE: 🟢 DIRECT  |  LEARNING PRIORITY: 🟠 MEDIUM

3. BlackX — why "patched" is a lie you tell yourself

WHAT HAPPENED: APT41-attributed UEFI bootkit against Central Asian diplomatic targets, rebuilt from BlackLotus, exploiting CVE-2022-21894 — a bug patched in 2022. It works because the real fix required a manual step (adding "Windows Production PCA 2011" to the Secure Boot DBX forbidden list) that organisations skipped. Kaspersky assess the attackers rebuilt BlackLotus specifically because they expected that step to be missing. The certificate expired on 19 Oct 2026, which changes nothing — only blocklisting stops the vulnerable binaries loading.

TERM: UEFI bootkit

SIMPLE MEANING: UEFI is the firmware that runs before your operating system. A bootkit infects that layer, so it loads before Windows and before any antivirus — which means it can lie to everything that comes after it. Reinstalling the OS doesn't remove it.

TERM: Secure Boot revocation / DBX

SIMPLE MEANING: Secure Boot only runs code signed by a trusted certificate. When a signed thing turns out to be vulnerable, the fix is to add it to a blocklist (the DBX forbidden list) so it's refused. Patching the software doesn't help if the old vulnerable signed version is still trusted.

WHY SHOULD I CARE? ⚪ The technology: not your field, ever. 🔥 The lesson: directly yours.

"Patch applied" ≠ "vulnerability closed." A four-year-old patched CVE is being exploited in 2026 because the patch had a second half that nobody performed. You will meet this exact shape in your own work:

  • npm audit fix updates package-lock.json — did you rebuild and redeploy? The running container has the old code.
  • You patched Node this morning per the Brotli advisory — does your Dockerfile base image still pull a vulnerable build on the next CI run? Then your next deploy silently reverts the fix.
  • You rotated a leaked key — did you also revoke the old one? That's LiteLLM's entire breach, and it's the same two-step pattern.

Notice the structural repetition: BlackX, the Brotli multi-runtime fan-out, and LiteLLM are all the same failure. Somebody did step one, believed they were done, and never did step two.

WHAT SHOULD I LEARN? Verify remediation at the point of execution, not at the point of intent. Don't check the lockfile — check what the running process reports.

SAFE PRACTICAL LAB: After this morning's Node upgrade, exec into your actual deployed container and run node -p "process.version". Not your laptop. The thing serving traffic. Then check whether your Dockerfile pins a version or floats on a tag.

🧠 CONTEXT ENGINEERING — THE DISCIPLINE NOBODY NAMED PROPERLY

Drew Breunig gave a talk at AGNTCon on 24 Oct 2026 and published the transcript. He has a book coming (The Context Engineering Handbook, O'Reilly). It's the clearest free writing on this subject right now. Status: ANALYSIS (expert opinion, not an announcement).

TERM: Context engineering

SIMPLE MEANING: Deciding what information goes into a model's context window, in what order, and what gets left out. Not prompt wording — information architecture.

The history, in short, because it explains the whole field

End of 2024 was the "RAG is dead" moment. The hope: make the context window big enough and you can stop being selective — put everything in, let the model sort it out. Context windows jumped from ~128K to a million tokens with Gemini 1.5. Llama 4 Scout shipped 10 million tokens.

It didn't work. In Breunig's words, inference was a challenge and Scout never caught on. More context created more problems, and he names four distinct failure modes. Two he describes directly:

  • Context poisoning — something false gets into the context (a hallucination, a bad fact) and the model can't get past it. It now reasons from a wrong premise for the rest of the conversation.
  • Context distraction — the model has so much material that it fixates on the wrong part of it.

His framing of the job is the line worth keeping: "knowing when to be deterministic and when to be probabilistic."

WHY DOES THIS MATTER TO ME?

Because it's the same conclusion as the System One story, arriving from a completely different direction. Not everything should be a model call. If a step can be done with code — a database lookup, a regex, an if-statement, a typed extraction model — doing it with an LLM is slower, costlier and less reliable. The engineering skill is drawing that line.

And context poisoning in particular is a backend problem with a backend solution: if a bad fact entering context is unrecoverable, then your agent needs the ability to discard and rebuild context — which means context has to be state you manage deliberately, not a chat array you append to forever.

WHAT SHOULD I LEARN? Context as managed state: what you include, what you summarise, what you drop, and when you reset. Start by reading the transcript — it's free and it's one sitting.

RELEVANCE: 🟢 DIRECT  |  LEARNING PRIORITY: 🟠 MEDIUM  |  ACTION: READ IT. dbreunig.com — The State of Context Engineering
