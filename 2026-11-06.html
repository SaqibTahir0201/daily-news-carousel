1. Next.js shipped 7 security fixes — your caching code may be leaking other users' data

WHAT HAPPENED: On 3 November Vercel released Next.js 16.4.5 and 15.5.29 fixing seven vulnerabilities. The worst ones let a cached page or cached function result generated for one user or one tenant get served to a different user. One more bug leaks HttpOnly cookies through an internal response header on Edge routes.

WHAT IS THIS? "Cache Components" is the Next.js 16 feature where you mark a function or component with 'use cache' and Next.js stores its output so it doesn't have to be recomputed. 2. AI agents can now be hacked through other AI agents

WHAT HAPPENED: Ars Technica reported that Google, JPMorgan Chase, Rapid7, the French government's digital directorate and others all acknowledged the same class of flaw: an attacker plants instructions in content, one agent reads it, and passes it down the chain to a second agent — which obeys, because it trusts internal agents. WHY IT MATTERS TO ME: You already run MCP in Hermes. The moment you build an agent for a client, you own this risk. And the fix is pure backend engineering — input validation, allow-lists, SSRF guards — which is the skill you are already trying to grow.

2. MCP "protocol pivoting" — the first real agent-to-agent attack class

WHAT HAPPENED: See item 2 above. Five unrelated organisations, same flaw class, over five months.

WHAT IS THE TECHNOLOGY?

TERM: SSRF (Server-Side Request Forgery)
SIMPLE MEANING: You trick a server into making a network request on your behalf — usually to somewhere you could never reach yourself, like the company's internal network.
REAL-WORLD EXAMPLE: Your Express app has POST /fetch-preview that takes a URL and fetches it to build a link preview. An attacker sends http://169.254.169.254/latest/meta-data/ — the AWS metadata endpoint — and your server happily fetches your cloud credentials and returns them.
WHY IT MATTERS: It is one of the OWASP Top 10, and AI agents multiply it because agents fetch URLs constantly.
WHY IT MATTERS TO ME: Any "fetch this URL" or "call this webhook" endpoint you write in Node is a candidate. Google's MCP toolbox got an 8/10 CVE for exactly this.
WHAT I SHOULD DO: Learn + fix. Validate the resolved IP, not just the string; block private ranges; refuse to follow redirects into them.

TERM: Zero trust
SIMPLE MEANING: Assume every part of your own system might already be compromised, and make each part prove who it is before doing anything sensitive.
REAL-WORLD EXAMPLE: Your "order service" should not accept "delete all users" just because the request came from inside your own network.
WHY IT MATTERS TO ME: This is the correct mental model for every multi-agent system you will build. Agent A asking Agent B to do something is untrusted input.

🤖 AI & AI AGENTS

The MCP Gateway pattern — the most useful architecture idea in today's news

WHAT IS IT? A paper (arXiv 2607.15593) describes a production system that sits between AI agents and thousands of MCP tool servers, instead of letting each agent connect directly to each server.

WHAT PROBLEM DOES IT SOLVE? Four problems, and every one of them is a classic backend problem wearing an AI costume:

  1. Too many tools for one context window. An agent can only "hold" maybe 20–50 tool definitions before token cost and latency explode and accuracy drops. But a company may have 3,000+ tools.
  2. Legacy APIs aren't MCP. They have 315 existing OpenAPI services that agents can't call.
  3. Auth and access control were being reimplemented in every single tool server.
  4. Session affinity. Stateful MCP servers run as multiple copies; requests in one conversation must keep hitting the same copy.

HOW DOES IT WORK? (simplified)

  • OpenAPI → MCP compilation: the gateway reads an OpenAPI spec and auto-generates one MCP tool per endpoint. Your existing Express REST API becomes agent-callable without rewriting it.
  • Tool retrieval instead of tool mounting: rather than giving the agent all 3,000 tools, a hybrid search engine (keyword + vector) retrieves the ~15 most relevant tools for the current task. They report ~98% Top-15 recall.
  • Session-aware routing: normal load balancers route on URL and headers. MCP puts the tool name and arguments in the HTTP body, so an ordinary L7 load balancer can't route it. The gateway inspects the body.

WHY ARE PEOPLE USING IT? Because the naive "agent connects directly to every MCP server" model collapses the moment you have more than a handful of tools — exactly the way "frontend calls every microservice directly" collapsed and gave us the API Gateway pattern.

WHY DOES IT MATTER TO ME? This is the clearest example I've seen of AI agent infrastructure being ordinary backend engineering: a gateway, a router, a retrieval index, an auth layer. You already understand API gateways conceptually. This is the same shape. It is the bridge between the MERN skills you have and the agent skills you want.

HOW COULD I USE IT IN A REAL PROJECT? Build a tiny Express service that (a) reads a JSON list of 50 fake tools, (b) exposes POST /tools/search that returns the 10 most relevant for a query string, and (c) exposes POST /tools/call that proxies to the real endpoint. That is a toy MCP gateway, and it is a genuinely impressive portfolio piece in late 2026.

WHAT SHOULD I LEARN? Tool retrieval (why too many tools hurts accuracy), the API Gateway pattern, and session affinity / sticky routing.

DO I NEED TO LEARN THIS NOW? Yes — this is the highest-value AI concept in today's news for you specifically.

RELEVANCE: 🟢 DIRECT  |  LEARNING PRIORITY: 🔥 HIGH  |  DEPTH: LEARN DEEPLY + BUILD

Status: ANALYSIS / EARLY — one company's production paper, not an industry standard. The pattern is sound; the specific numbers are theirs.

💻 MERN / JAVASCRIPT / WEB

Cache Components and 'use cache' — what actually changed

WHAT CHANGED? Seven CVEs patched. But more useful to you: this incident finally forces a clear explanation of a Next.js 16 feature most developers use without understanding.

WHAT IS CACHE COMPONENTS? A Next.js 16 model where caching is explicit. You write 'use cache' at the top of a function or component, and Next.js remembers its output. Nothing is cached unless you say so.

WHY WAS IT CREATED? Because the old Next.js caching was implicit and nobody could predict it. In Next 13/14 you'd ask "why is my page stale?" and the answer was buried in four overlapping cache layers. Cache Components replaced guessing with a directive you can see in the code.

HOW DOES IT WORK? Next.js computes a cache key from the function's arguments plus the "root parameters" it reads (tenant, locale, etc.). Same key → reuse the stored result. The bugs this week were all the same shape: the key was incomplete, or the entry was written before the key was fully known.

SIMPLE EXAMPLE:

async function getDashboard(tenant) { 'use cache'; return db.collection('stats').findOne({ tenant }); }

Correct behaviour: getDashboard('acme') and getDashboard('globex') are two different cache entries. The bug: under a cold cache with a concurrent unstable_cache call, 'globex' could receive 'acme''s stored result.

WHAT EXISTING CONCEPT DOES IT REPLACE OR IMPROVE? It replaces implicit fetch-level caching and the old unstable_cache. Mixing the two is literally what caused the worst bug — so treat unstable_cache as legacy.

WHY SHOULD A NEXT.JS DEVELOPER CARE? Because the mental model transfers everywhere. In Express + Redis you'd write cache.get('dashboard:' + tenant). If you ever write cache.get('dashboard') and forget the tenant, you have just reimplemented CVE-2026-119790 by hand.

SHOULD I LEARN IT? HOW DEEPLY? 🟢 DIRECT, 🔥 HIGH, LEARN DEEPLY. This is a one-hour topic with a career-long payoff.

WHAT SHOULD I LEARN? Cache keys, cache invalidation, stale-while-revalidate, and the difference between a private cache (per user) and a shared cache (everyone).

The other Next.js fixes worth knowing as patterns

  • HttpOnly cookie exposure on Edge routes (GHSA-f3mh-rxg3-f5g2). HttpOnly means "JavaScript in the browser must not be able to read this cookie" — the main defence that stops an XSS bug from stealing session tokens. Next.js was copying the cookie into an internal header, x-middleware-set-cookie, which is readable by same-origin JavaScript. Lesson: a security property is only as strong as every place the value gets copied to.
  • SVG rejection bypass in image optimization (GHSA-7qx7-33qx-rqx2). You set images.dangerouslyAllowSVG: false to block SVGs (SVGs can contain scripts). An attacker's image was mis-detected as AVIF, got past the check, and then the backend decoded it as SVG anyway. Lesson: never trust the file extension or the declared content type — detect the actual format, and detect it once.
  • Cross-client response injection behind an HTTP/1.1 proxy (GHSA-pc58-hwjq-p385). A self-hosted app returned a fetched Response unchanged, forwarding decompressed bytes with the compressed response's Content-Length. Behind a proxy reusing one backend connection, the length mismatch made responses get handed to the wrong clients. This is a classic HTTP request smuggling / response-splitting shape. Lesson: if you proxy a fetch result in a Route Handler, strip the encoding headers.

RELEVANCE: 🟢 DIRECT  |  LEARNING PRIORITY: 🟠 MEDIUM  |  DEPTH: UNDERSTAND THE BASICS

One practical note: if you host on Netlify, three of the seven don't affect you, but you also need adapter @netlify/plugin-nextjs 5.16.6 for the middleware cookie case — upgrading Next.js alone is not enough there.

🏗️ TODAY'S SYSTEM DESIGN CONCEPT

CONCEPT: Cache Key Design & Cache Isolation

IN ONE SENTENCE: A cache key is the "name" you file a stored result under — and if two different things end up with the same name, one user gets another user's data.

WHAT PROBLEM DOES IT SOLVE? Caching makes things fast by not recomputing. Cache key design is what makes caching correct. Everyone learns the first half; the second half is what separates a junior from a senior.

SIMPLE REAL-WORLD EXAMPLE: A coat check at a restaurant. You hand over your coat and get ticket #42. If the attendant gives two people the same ticket number, someone goes home in a stranger's coat. The ticket is the cache key. Today's Next.js CVEs are exactly this: two tenants, one ticket.

HOW IT WORKS: Three rules.

  1. Completeness — every input that changes the output belongs in the key. Including the invisible ones: user ID, tenant, locale, role, feature flags, API version.
  2. Isolation — if two requests must never see each other's data, their keys must never collide. Namespace them: tenant:acme:user:123:dashboard.
  3. Write-after-complete — don't store the entry until you know everything the key depends on. Next.js stored early and got bitten.

WHERE IS IT USED? CDNs (the Vary header is literally a cache key declaration), Redis, HTTP browser cache, React Query, GraphQL clients, and now LLM response caches.

HOW WOULD I USE IT WITH NODE/EXPRESS/MONGODB?

Bad:
const key = 'dashboard';
let data = await redis.get(key);
if (!data) { data = await db.collection('stats').find({ tenant: req.user.tenant }).toArray(); await redis.set(key, JSON.stringify(data), 'EX', 60); }

Every tenant now shares one entry. The first tenant to hit the endpoint decides what everyone sees for 60 seconds.

Good:
const key = `v1:dashboard:tenant:${req.user.tenant}:role:${req.user.role}`;

Note the v1: prefix — when you change the shape of the cached data, bump it to v2: and every old entry becomes unreachable instantly. That is the cheapest cache invalidation strategy in existence.

COMMON MISTAKE: Caching a response that depends on the logged-in user in a cache that is shared between users. The sneaky version: the endpoint is public today, someone adds a "personalised greeting" six months later, and nobody updates the key.

SECOND COMMON MISTAKE: Caching the result of an authorization check. Cache the data; re-check permission on every request.

WHAT I SHOULD BUILD TO LEARN IT: A small Express + MongoDB + Redis app with two tenants and a /dashboard endpoint. First write it with the broken key. Log in as tenant A, then tenant B, and watch yourself see A's data. Then fix the key. Seeing the leak with your own eyes is worth ten articles.

🎨 CREATIVE DEVELOPMENT

TSL (Three.js Shading Language) — and why today's data settles the question

WHAT IS IT? TSL lets you write GPU shader logic as JavaScript function calls instead of as GLSL source strings. Three.js builds a graph of what you wrote (a "node graph") and then compiles it to WGSL for WebGPU or GLSL for WebGL2, depending on what the browser supports.

Old way — a GLSL string, no autocomplete, no type checking, errors at runtime as a wall of red text.

New way:
import { texture, uv } from 'three/tsl';
const detail = texture(detailMap, uv().mul(10));
const material = new THREE.MeshStandardNodeMaterial();
material.colorNode = texture(colorMap).mul(detail);

That is JavaScript. Your editor autocompletes it. TypeScript can type it. And it runs on both WebGPU and WebGL.

WHY IS IT BECOMING IMPORTANT? Because the maintainers have voted with their commits. Across r185, r186 and r187, 79–82% of all core changes went to the WebGPU/TSL side. The classic WebGL renderer got 2%, 11% and 14%. Meanwhile the three/tsl export surface grew from 638 to 819 names in two releases while plain three stayed flat at ~443.

WHAT CAN IT DO? Everything GLSL can, plus: automatic shader-graph optimisation, deduplication (you don't have to care what order you declare things in), and compute shaders — running general-purpose parallel math on the GPU, which WebGL simply could not do.

TERM: Compute shader
SIMPLE MEANING: A program that runs on the GPU to do raw calculation, not to draw pixels.
REAL-WORLD EXAMPLE: Simulating one million particles with gravity and collisions. On the CPU in JavaScript that's a frozen tab. On the GPU it's 60fps, because the GPU does thousands of those little calculations simultaneously.
WHY IT MATTERS: It is the single biggest capability WebGPU adds over WebGL, and it's what the next generation of Awwwards sites will be built on.
WHY IT MATTERS TO ME: This is your differentiator. Plenty of developers can do a scroll-triggered GSAP timeline. Far fewer can do a GPU-driven particle system.
WHAT I SHOULD DO: Experiment — later, after TSL basics.

WHY SHOULD I CARE? Because you are at the point of choosing what to learn. Today's data says: learn TSL first, GLSL second. The fallback makes this safe — WebGPURenderer automatically drops to a WebGL2 backend when the browser lacks WebGPU, and your node materials keep working. You are not betting on the future; the future already ships with a parachute.

WHAT CAN I BUILD WITH IT? Start tiny: a plane with a MeshStandardNodeMaterial whose colour is driven by sin(time) mixed between two colours. ~15 lines of TSL. From there: displacement on a sphere, then scroll-driven distortion, then particles.

WHAT SHOULD I LEARN FIRST? In order: (1) node materials vs standard materials, (2) the core TSL nodes — uv(), time, positionLocal, color(), mix(), sin(), (3) colorNode and positionNode, (4) uniforms. Stop there. Do not start with compute shaders or RenderPipeline.

RELEVANCE: 🟢 DIRECT  |  LEARNING PRIORITY: 🟠 MEDIUM  |  DEPTH: EXPERIMENT

Honest caveat: MEDIUM, not HIGH, because the backend/security items above pay your bills sooner. But this is the one you'll enjoy most, and the official TSL spec at threejs.org/docs/TSL.html is genuinely good.

One upgrade warning for r187: CubeUVReflectionMapping was removed, light registration changed, and PMREM now uses cube render targets — which can change how your existing materials look. Don't upgrade an in-progress project mid-week.

🛡️ CYBERSECURITY

Vulnerability of the day: cross-tenant cache disclosure (CVE-2026-119790 and friends)

WHAT HAPPENED? Covered above — seven Next.js advisories, four of them cache-related.

WHAT IS THE VULNERABILITY? Information disclosure through cache key collision. No injection, no broken crypto, no clever payload. The application correctly generated the content and then handed it to the wrong person.

HOW DOES THE ATTACK WORK? (defensive description only) The attacker doesn't inject anything. They make ordinary requests, timed so that their request arrives while another tenant's cache entry is being filled. The framework's bookkeeping loses track of whose entry it is. The attacker receives data they were never authorised to see. The only "skill" required is timing and patience — which is what makes it dangerous.

WHO IS AFFECTED? Next.js 16.2+ apps using Cache Components (several variants), and 15.x/16.x for the image-optimizer issue. Self-hosted apps running next start are affected by two issues that managed platforms are not.

WHY SHOULD A MERN DEVELOPER CARE? Because you will write this exact bug yourself in Express + Redis. Frameworks get CVEs and patches; your handwritten cache gets neither. Nobody is going to publish an advisory for your app.js.

HOW DO I PROTECT MY APPLICATION?

  1. Upgrade to next@16.4.5 / next@15.5.29 today. On Netlify also take adapter 5.16.6.
  2. After upgrading, purge your caches. Patched code does not clean out poisoned entries written by the old code.
  3. Stop mixing unstable_cache and 'use cache' for the same function.
  4. In your own Express code: namespace every cache key with the tenant and user, version the prefix, and never cache the result of a permission check.
  5. For the cookie issue: set cookies via cookies().set() in Node.js Route Handlers rather than NextResponse.cookies.set() in Edge routes where you can.

WHAT SHOULD I LEARN? Cache poisoning, the Vary header, private vs shared caches, and the basics of HTTP request smuggling (for the proxy issue).

🔮 WHERE TECHNOLOGY IS GOING

TREND 1: Agent infrastructure is becoming ordinary backend engineering.
WHAT THAT MEANS: The hard problems in AI agents today are gateways, routing, retrieval, rate limits, session affinity, auth and caching. Not prompts.
WHY IT MATTERS: The "AI engineer" title is quietly converging on "backend engineer who understands LLMs." That is excellent news for you.

TREND 2: Security is arriving at agents late, and it's all old bugs.
WHAT THAT MEANS: SSRF, injection, missing authorization, trusting internal callers. The industry built sprawling agent networks and skipped zero trust.
WHY IT MATTERS: There is a hiring gap opening between people who can build agents and people who can build agents safely.
WHAT I SHOULD LEARN: The OWASP fundamentals, applied to agents. Your advantage is that the underlying bugs are twenty years old and well documented.

TREND 3: AI training data has become a supply-chain dependency.
WHAT THAT MEANS: MCPhantom showed agents installing dead packages because the names were in the model's memory. Your model's training cutoff is now part of your dependency graph.
WHY IT MATTERS: It's a brand-new attack surface, and the usual defences (lockfiles, audits) don't catch it — the agent adds the dependency after your review.
WHAT I SHOULD LEARN: Review what your agents install. Pin and audit. Never let an agent add a dependency unreviewed.

TREND 4: Browser 3D is completing its move to WebGPU.
WHAT THAT MEANS: WebGPU shipped across all major browsers in late 2025, and Three.js now spends ~80% of its core effort on the WebGPU/TSL path. Shaders are becoming JavaScript.
WHY IT MATTERS: GPU compute arrives in the browser, which raises the ceiling on what a website can do — and lowers the barrier for JS developers who were blocked by GLSL.
WHAT I SHOULD LEARN: TSL, node materials, then compute shaders.

TREND 5: Frameworks are shipping explicit caching, and pushing the correctness burden to you.
WHAT THAT MEANS: Next.js moved from implicit magic caching to explicit 'use cache'. More control, more responsibility.
WHY IT MATTERS: "The framework handles it" is no longer an answer. Understanding caching is becoming mandatory for frontend-adjacent developers, not just backend ones.
WHAT I SHOULD LEARN: Cache keys, invalidation, isolation. Same as Trend 1's foundation.
